# Resound architecture

State as of v0.13.0-dev (keybinds per app and mouse buttons as hotkeys). For building and icons, see [BUILDING.md](BUILDING.md); for releases, [RELEASING.md](RELEASING.md).

## What it is

Resound is a Windows tray app that plays sounds into a virtual audio cable (so others hear them in games or voice chat) and to your own speakers. It is controlled from a phone app (a web app installed from an HTTPS host) that connects to the PC directly over the local network. It replaces the Soundux desktop app (C++/WebView2) with one Go executable: no cgo and no UI framework, ~9k lines.

```
 phone app ──WebRTC────▶ server ──Player──▶ app (UI thread) ──▶ audio.Engine ─┬─▶ "You hear"   WASAPI stream ─▶ speakers
 (webapp/, hosted)         │                  │                                └─▶ "Others hear" WASAPI stream ─▶ CABLE Input
                         library           routing / input                                      │
                                           (mic mute, PTT)        mic ─"Listen to this device"─▶┘ CABLE Output ─▶ game / Discord
 tray icon ─▶ popup panel (ui) ───────────────▲
```

## Processes and entry points

One executable, `cmd/resound` → `app.Run()`. The first argument selects a role:

| Invocation | Role | Elevated |
|---|---|---|
| *(none)*, `--autostart`, `--welcome=install\|update` | Tray app. A non-portable exe outside the install folder installs itself first | no |
| `--resume-setup` | Tray app, started again after the restart a VB-Cable install needs, by Windows' restart-apps registration or `RunOnce` (what to resume comes from `vbcable-install.json`) | no |
| `--apply-routing --input=… --target=… --enable=…` | Writes "Listen to this device" on a mic, verifies, exits | yes (UAC) |
| `--allow-firewall` | Replaces the exe's firewall rules with one allow rule, exits | yes (UAC) |
| `--uninstall` | Confirm dialog, then removes app, registrations and data | no |
| `--restore=<zip> --wait-for=<pid>` | Tray app started by "Restore": waits for the old instance to exit, saves a safety backup, restores the zip, then runs normally | no |

Helper roles run before the single-instance mutex (`Local\Resound.SingleInstance`). A second tray start sends `wmShowPanel` to the running instance, which opens its panel. The installer and uninstaller send `wmQuitApp`, which makes the running instance quit.

## Threading model

- **UI thread.** The goroutine that calls `ui.NewTray` is locked to its OS thread and runs the message loop. All `App` state lives here.
  - Other goroutines reach it with `Tray.Post(fn)`, which queues `fn` and posts `wmInvoke`.
  - Server handlers use `App.onUI(fn)`: Post, then wait up to 3 s.
- **Audio threads.** Each output has its own goroutine, locked to an OS thread with COM (MTA) and MMCSS "Pro Audio" priority. It runs an event-driven render loop and owns all of that stream's COM objects. The mixer's lock only guards its voice list.
- **COM calls from the app** (device lists, mute, routing checks) go through `wincom.Run`: a fresh locked MTA thread per call. The UI thread is apartment-threaded (STA) only for shell dialogs.
- **Server.** Standard `net/http` goroutines. Read-only queries go straight to the thread-safe `library` and `engine`. Anything that changes app state goes through `onUI`. Decoding happens on the HTTP goroutine, never on the UI thread.
- **Meter threads.** While the audio flow is on screen, the mic meter and the "CABLE Output" meter each record on their own locked COM thread (`audio/meter_windows.go`) that owns their COM objects; the panel takes their peaks from atomics.
- **Engine events** (first buffer, finished, output failed) go into a 256-slot channel without blocking the render thread. `pumpEvents` forwards them to the UI thread.
- **Dialogs** (`ui.TryConfirm`) run on their own locked thread with their own message loop. They work in processes without a tray.
- **Hotkey hook.** While a pause, stop or overlay key is set, or an app has keybinds of its own, `input.Watcher` runs a low-level keyboard hook on its own locked thread with its own message loop; the low-level mouse hook and a WinEvent hook for foreground changes run on the same thread. The callbacks only update the `Matcher` and post events to the UI thread (`Tray.Post`): Windows silently drops hooks whose callback is slow. The push-to-talk hand-over (below) sends its keys from this thread's loop, never from the UI thread, so a busy panel can't delay the user's key.
- **Elevated helpers** are separate processes started through `elevate.Run`, waited on from a goroutine, with results posted back.

## Audio pipeline

- **Outputs.** There are two roles: `monitor` ("You hear", empty ID = system default) and `cable` ("Others hear", empty ID = automatic: VB-Cable's CABLE Input once it is installed, opened as soon as it appears; off without it).
  - Each role is one long-lived shared-mode WASAPI stream with a 20 ms requested buffer (22 ms measured), opened in about 10 ms.
  - The stream writes the device's mix format: 32-bit float or 16/24/32-bit integer, 1–8 channels. Stereo goes to front left/right, mono gets (L+R)/2.
  - **Errors** (`audio/deviceerr.go`). WASAPI fails with `AUDCLNT_E_*` HRESULTs that have no message text in Windows, so go-ole's text for them was only `FormatMessage` failing ("The system cannot find message text for message number 0x%1…"). `describeHRESULT` names them instead, and output errors name the device and the step: `monitor output: "Speakers (Realtek)": Initialize: another app is using this device exclusively (AUDCLNT_E_DEVICE_IN_USE)` in the log and Diagnostics. The panel (the flow's "Output failed" tooltips, the line under the flow) shows only `audio.Problem`, built from the engine's current state on every render (`outputErrorRows`), so it goes as soon as a device that works is chosen or the outputs restart: a few words for known causes, "the device couldn't be opened" otherwise. `AUDCLNT_E_DEVICE_IN_USE` in shared mode means another app holds the device in exclusive mode, typically a mixer such as Voicemeeter or SteelSeries Sonar that took the hardware for itself (seen on the dev PC when picking such a device for "You hear").
- **Volume curve** (`audio/volume.go`). Volume percentages (the panel's sliders, per-sound volumes) become gain through `audio.Gain`: linear in decibels over 40 dB up to 100%, so loudness changes evenly along the slider (75% = −10 dB, 50% = −20 dB, 25% = −30 dB, 10% = −36 dB), then a linear fade to true silence at 0%. Per-sound boosts above 100% stay linear (200% = +6 dB). `audio.Percent` is its inverse. Configs from before 0.9 (no `volumeScale` in `config.json`) were saved on a linear scale; `migrateVolumeScale` converts the defaults and every per-sound volume once to the percentage with the same loudness (50% → 79%).
- **Loudness normalization** (`audio/loudness.go`). Every sound plays with the gain that brings it to âˆ’16 LUFS (`audio.NormGain`), applied by its decoder before any volume, so volumes (defaults and per-sound) act on top of it. Settings â†’ Sound library â†’ "Even out the loudness of sounds" turns it off (`noNormalize` in `config.json`); sounds not measured yet play unchanged.
  - The measure is ITU-R BS.1770-4 integrated loudness (as in EBU R 128): K-weighted energy over 400 ms blocks every 100 ms, gated at âˆ’70 LUFS and 10 LU below the average, so silence and quiet tails don't count and a single sharp impact barely moves it. Clips shorter than one block are measured as one block. The K-weighting is derived for the file's own sample rate (no resampling); at 48 kHz it is the standard's. Mono files count as two channels, as they play. Measured against ffmpeg's `ebur128` on the developer's library: 0.09 LU apart on average.
  - Quiet sounds are boosted by at most 12 dB, and only until their robust peak (the level only the loudest 0.1% of frames exceed, from a histogram binned on the float's bits, without a logarithm per sample) reaches full scale. Transients above it are rounded off by the mixer's soft clipper rather than holding back the whole sound.
  - Speed: MP3s are decoded by go-mp3 directly from memory (beep's wrapper converts every sample with `math.Pow`, a fifth of the time); files over 90 s (songs) are measured as six 10 s segments spread over the file (0.4 LU from a full measurement on average). go-mp3 decodes ~85Ã— real time per core; the indexer measures on up to 4 workers. A library of 151 sounds (110 clips, 41 songs, 2h43m) takes ~10 s, the clips alone ~2 s.
  - An import's preview measures the new file on the spot, as the indexer usually hasn't reached it yet.
- **Mixer.** Sums voices into stereo float32 and soft-clips: samples up to 0.9 pass unchanged, louder ones bend along a tanh curve towards Â±1.
  - A voice has a gain that either scales the role volume or, for per-sound custom volume, replaces it. The play reads a sound's custom volumes on the UI thread just before it starts, and a change from the phone is applied to playing voices on the UI thread too (`SetSoundVolume`), so a change made while a sound is decoding can't miss it.
  - The same voice ID is queued on both mixers, so the two copies start in the same device period. Pause and stop address both copies by ID.
- **Streaming playback.** Every play decodes the original file while it plays (`gopxl/beep`: mp3, wav, flac, ogg, resampled to the output rate). Nothing decoded is kept in memory or on disk after a sound ends.
  - One producer goroutine (one decoder) per sound and distinct output sample rate fills a 500 ms single-producer/single-consumer ring buffer per output. With both outputs at 48 kHz, a sound is decoded once. The mixer drains its ring on the render thread without locks, blocking or disk access; a producer that falls behind causes silence, not an error.
  - Memory per playing sound is fixed (~190 KB per output at 48 kHz) whatever the file's length.
  - `PrepareSound` returns once 100 ms are decoded, before the mic is muted. Measured on Linux from the OS file cache: ~1.5 ms for a 10-minute WAV, ~3 ms for a 60-minute MP3.
  - MP3 files are opened without `Seek`: given a seekable file, the decoder parses every frame of the file before the first sample (114 ms for a 60-minute file even from the OS cache). The length comes from the index instead.
  - When a sound was decoded to its end, its exact length is stored in the index (`exactLength`).
  - Stop, finish and output shutdown (`Mixer.Drain`) close sources; a producer stops and closes its file when none of its sources is left.
- **Level meters** (`levels.go`, `meter_windows.go`). Peaks are held in atomics (`peakHold`: raised by the audio thread, taken and reset by the panel ~30 times a second) and shown on a decibel scale from −54 dB (`MeterPosition`).
  - Each mixer keeps the peak of its voices before the master volume (the sounds themselves; a sound with a custom volume relative to the master, so one turned down to 0% shows nothing) and of its final mix; `Engine.Levels` takes them. Sources track their own peak while mixing, so this costs a compare per sample.
  - `InputLevel` records from a capture device only to measure it: the microphone, and VB-Cable's "CABLE Output" (exactly what others' apps receive: the sounds and the routed mic). Windows meters a capture device (`IAudioMeterInformation`) only while some app records from it, which is why the bars in Windows' Recording tab only move while that dialog is open. While it runs, Windows 11 shows its microphone-in-use icon. If the privacy settings block desktop apps from the microphone, it fails with `ErrMicBlocked`.
  - Windows' own meter of VB-Cable's devices is not used: measured on the dev PC, after a 0.45 s chime it still read half its peak after 1 s and had not reached zero after 4 s, while the samples recorded from CABLE Output were silent ~0.1 s after the chime ended. The Sound dialog shows the same slow tail.
- **Test sound** (`ChimeSource`): a quick rising A minor 9 arpeggio of glassy FM plucks with a darkening ping-pong echo, over a soft detuned pad, landing on two low notes; through a gentle 2.4 kHz low-pass, 3 s, long enough to watch it in the audio flow, generated in memory. `go test ./internal/audio -run Chime` with `RESOUND_RENDER_DIR` set saves it as a WAV.
- **Measured on the dev PC:** 0.5–10 ms from play to the first device buffer, plus the 22 ms buffer.

## Playback holds: mic mute and push-to-talk

While sounds play for others (any non-preview play), `holdPlayback` does two things, each if enabled:
- mutes the real mic (`IAudioEndpointVolume`), never touching a mic the user muted themselves, but only while a **long** sound plays (below);
- presses push-to-talk, for every sound.

`releasePlayback` runs when the last voice finishes, on stop-all and on output failure.

**Which sounds mute the mic** (`app/mutemic.go`, `muteFor`, `longPlaying`). "Mute my microphone while sounds play" (`muteMicWhilePlaying`, off for new configs since 0.13: it confused many; saved configs keep theirs) has a threshold, "Minimum sound length" (`muteMicMinSeconds`, 5 s; configs from before it get 5 s through `Default`): a sound mutes the mic when it is longer than that, or of unknown length (0: neither the library nor the decoder knows it; muted, as before), and with 0 ("Always", anything under 1 s) every sound does. The length is the one known when the sound starts (`Prepared.Length`: the library's, else the decoder's estimate), stored with the voice (`voiceMeta.length`).
- The mic is muted while at least one voice for others that mutes it plays, not paused (`longPlaying`, from the engine's voices and `remaining`). Each sound counts on its own: short sounds one after another never add up.
- `start` mutes before the new voice starts, if it is long (it isn't in the engine yet) or a long one plays. When a voice finishes and others remain, the mic is let go once no long one is left (a short sound still playing then leaves it open). Resuming after a pause holds again only for long voices. Changing the switch or the threshold judges what plays now again (`syncMic`; switched off, the mic is let go at once).
- The threshold steps through `muteSteps` (Always, 1–10 s, then 12, 15, 20, 25, 30, 45, 60, 90, 120, 180, 300, 600 s) with − and +, or takes a typed value (`ui.StepperEdit`: its underlined value opens a text field; "7.5", "7,5" and "7 s" work, rounded to a tenth, at most 600 s, under 1 s "Always"). It shows only while the switch is on.

Push-to-talk uses **reasons** (`playback`, `talk`). The keys go down when the first reason appears and up when the last one goes away. Talk-through adds `talk` before pausing the sounds, so the key never bounces during the hand-over.

Pause, talk-through and a held pause key pause the active voices and release the mic and PTT. Resuming holds them again, but only if the voices still exist. Only one of the three owns the pause at a time; the others wait until it ends.

**Hotkeys** (`app/hotkeys.go`, `input/hotkeys.go`, `input/hook_windows.go`): combinations of keys and mouse buttons that work anywhere, e.g. inside a game. Which ones apply depends on the app in the foreground (Keybinds, below).
- **Pause keys** pause while held (`setHoldPause`): sounds pause, the mic is unmuted and push-to-talk released (before the game sees the key: the hand-over below), so the user can talk on another channel. Releasing the key resumes them and presses push-to-talk again, after 150 ms (`holdResumeDelay`): pressed right after the game saw the pause key go up (often its own push-to-talk for another channel), Resound's push-to-talk was sometimes missed by games.
  - The sounds stay paused meanwhile, so they never play without push-to-talk. Pressing the pause key again before then keeps the pause (and pauses sounds started meanwhile), so quick taps don't make push-to-talk bounce; the sounds resume 150 ms after the last release.
  - The phone's pause or talk-through within those 150 ms takes the pause over without resuming in between; a stop key or the phone's stop ends it. Changing the hotkeys resumes at once. A pause with nothing paused ends at once.
- **Stop keys** run `stopAll` once per press.
- Several combinations per action, recorded in the panel. Keys and mouse buttons 3–5 (middle, back, forward) work alike, alone or together (Ctrl + Mouse 4); left and right buttons can't be bound (they work the panel and aim in games). Left and right modifiers count as the same key.
- **Matching** (`Matcher`, portable and tested). An action starts on the press that completes one of its combinations; repeats don't count. A combination that becomes complete otherwise, because the bindings changed while its keys were held (another app in front, settings changed), does nothing until pressed again. A pause lasts while any pause combination is held, of the bindings that started it as well as of the current ones, so an app switch while a pause key is held never ends the pause early or makes it bounce; it ends with its keys' release. (Settings changes still end a pause at once in the app.)
- **Watching.** A low-level keyboard hook (`WH_KEYBOARD_LL`), installed only while a hotkey is set, an app has keybinds of its own, or the overlay's preview shows. For pause and stop keys it observes without swallowing anything, so the game still gets the key; `RegisterHotKey` would swallow it and can't take mouse buttons. The exceptions are the hand-over (below), which only holds the key back, and the overlay. Resound's own `SendInput` presses (keys and buttons) carry a marker in `dwExtraInfo` and are ignored. Keys and buttons the hook believes held are checked with `GetAsyncKeyState` every 250 ms, so a release lost to the secure desktop (UAC, Ctrl+Alt+Del) can't leave the sounds paused. Only "pause/stop key" events are logged, never keys.
- **Mouse buttons.** A low-level mouse hook (`WH_MOUSE_LL`) sees every mouse event system-wide, moves included, and each one waits for Resound's hook thread, so it is installed only while needed (`syncMouse`): while the bindings of the app in front hold a button, while the overlay is open (the wheel), and while a button it saw go down is still held or on its way (so its release isn't missed). Its callback returns at once for moves, and only the middle and side buttons are matched; the left and right buttons always pass. Button presses go through the same `Filter` and hand-over as keys.
- **Push-to-talk hand-over.** Many games end all transmission when any push-to-talk key goes up. A pause key is usually the game's push-to-talk for another channel, so if the game saw it go down before Resound let go of its own push-to-talk key, that release would cut off the user's talk too. Releasing faster can't help: by the time the hook returns, the user's key is already on its way to the game. So while sounds hold push-to-talk (playback is the only reason: not during talk-through, not while recording a key), the UI thread lends the held keys to the hook (`Watcher.LendPTT`, an atomic pointer).
  - The press that starts a pause or stop takes the loan in the callback (`Swap`, so the hook and the UI thread can't both release the keys) and is swallowed. The hook thread's loop then sends the push-to-talk release and that press in one `SendInput` call, which Windows inserts without other input in between, carrying the original virtual key and scan code. The game sees push-to-talk end, then the user's key. Measured: the key arrives about 0.5 ms after it was pressed.
  - The press is always passed on, also if the release fails or the watcher closes. If the message to the loop can't be posted, the key passes as it is.
  - Until the passed-on press has come back through the hook, the key's release is swallowed and re-sent after it (otherwise a release already waiting in Windows' input queue would reach the game first), and the 250 ms stale-key check leaves that key alone (`GetAsyncKeyState` still says it's up), for at most 1 s.
  - The UI thread takes the loan back before changing push-to-talk (`reclaimPTT`). If the hook used it, the keys are up already and only the state is updated. Releasing after a pause or stop then sends nothing; pressing again after a pause comes 150 ms after the key's release (above).
  - Only the key that completes a combination is held back (its other keys reached the game already); repeats pass. Keys the overlay takes stay with the overlay.
  - A mouse button is handed over the same way: its press is swallowed in the mouse hook and sent again with `SendInput` (at the pointer, which hasn't moved in between) after the push-to-talk release, its early release queued behind it. `TestMouseHandOverLive` (opt-in) checks it with Mouse 5; its observer swallows every Mouse 5 event, so the test's clicks reach no window.
  - The switch "Let go of push-to-talk first" (`noPushToTalkHandOver` in `config.json`) turns it off, for a game that ignores keys sent by other programs: the user's key then reaches it as one.
  - Checked with `TestHandOverLive` (opt-in): an observer hook behind the watcher's sees the push-to-talk release before the pause or stop key, and a press and release sent in one go stay in that order. Some keyboard tools take keys for themselves after Resound's hook (on the dev PC, F22 never counted as held), so the test uses F21, F23 and F24.
  - Limits: a program with its own low-level hook installed after Resound's sees the key first; the mic is unmuted and the sounds paused by the UI thread a few milliseconds after the key reaches the game.
- Like `SendInput`, the hook gets no keys while a program running as administrator has the focus.
- A sound started while a pause key is held plays normally (and holds push-to-talk).
- **The user's own push-to-talk** (`app/talk.go`, "My push-to-talk pauses sounds", on unless `noPushToTalkPauses`; only while "Hold push-to-talk while sounds play" is on). Resound holds the game's push-to-talk key, but the user can press the same key to talk; their release ends push-to-talk in the game while Resound still believed it held it, so the rest of the sound went unheard. The hook therefore reports the user's own presses of the push-to-talk combinations of the app in front (`Bindings.Talk`, `ActionTalk` with the combination's index; latched like a pause, never swallowed; Resound's marked presses don't count), and the key works like a pause key:
  - **Press.** The keys the user holds become theirs: Resound forgets them without a release (it would cut them off) and lets go of keys of its other push-to-talk combinations, as for a pause. While something plays, the sounds pause and the mic is let go (`setHoldPause`, shared with pause keys).
  - **Held.** Resound sends no push-to-talk key (`ptt.userTalk` blocks pressing, re-pressing on an app switch, the hand-over loan and "send to game"). Sounds started meanwhile play (as under a pause key) but don't mute the mic: the user is talking. The hook itself skips the hand-over while a talk is held (`Filter.Talking`), so a pause key pressed right after can't release the user's keys before the UI thread knows.
  - **Release.** It reaches the game. `holdResumeDelay` later, as after a pause key, the paused sounds resume and Resound presses push-to-talk again for what still wants it: those sounds, ones started meanwhile (muting the mic again for long ones), talk-through (`afterTalk`). Pressing again before then keeps the pause (`talkGen`). A pause held by a pause key and the user's push-to-talk together lasts until both are let go (`onPauseKey`).
  - **Races.** The hook publishes the talk at once (`Watcher.Talking`); before sending any push-to-talk key the UI thread starts a talk the hook knows about but whose event hasn't arrived (`catchUpTalk`), so a sound ending a moment after the user's press can't release the key under their finger. Closing the watcher ends a talk (no release will come). The watcher now runs whenever push-to-talk keys are set (by default).
  - **Limit.** Only a press that completes a push-to-talk combination counts: with a combination such as Ctrl + F, letting go of Ctrl alone still ends push-to-talk in many games.
  - Unit-tested with recorded key presses (`talk_test.go`: take-over, pressing again, several combinations, Resound's hold starting during a talk, the watcher closing, together with a pause key, which keys the hook gets) and live (`TestTalkLive`: the user's key passes, no hand-over while talking).

**Keybinds** (`app/keybinds.go`, `app/keybindpages.go`, `config.AppKeybinds`): push-to-talk, pause and stop, each with several combinations, globally and per app, and the overlay's key (one combination; its global card is on the overlay's page, an app's on the app's page).
- **Global keys** are the settings of earlier versions, unchanged: `pushToTalkKeys`, `pauseHotkeys`, `stopHotkeys`. Push-to-talk takes up to 4 combinations: the first stays in `pushToTalkKeys` (older versions keep reading it), the others go to `pushToTalkExtra`; all are held together (`pttUnion`: every key once, in order). Pause and stop take up to 8 each.
- **Apps** (`appKeybinds`) are known by their program's file name in lower case (`input.AppName`, e.g. `valorant-win64-shipping.exe`), the same across updates and install folders, with a display name from the file's version resource (`FileDescription`, else `ProductName`). Each function of an app has an override (`config.KeyOverride`): none (`nil`: the global keys apply there), keys of its own (which replace the global ones there), or `off` (no keys: the function is off there, "None" in the panel). An override whose last key is removed is no override. `config.Load` tidies what it reads (`cleanKeybinds`): empty combinations, duplicate or nameless apps, and overrides with neither keys nor `off` go.
- **The watcher's keymap** (`input.Keymap`): the global bindings, and for each app with an override its complete bindings, the global ones merged in (`App.keymap`). The hook thread follows the foreground window: a WinEvent hook (`EVENT_SYSTEM_FOREGROUND`, out of context, skipping Resound's own process), a look at `GetForegroundWindow` on every key or button event (a press right after a switch can come before the WinEvent), and the 250 ms timer as a fallback. A new foreground window is resolved to its program (`QueryFullProcessImageName`, only when the window changes) and matched with that app's bindings; a window of Resound's own (the panel) keeps the app before it, and so does Windows' shell UI that comes up over an app: windows of the shell's programs (`explorer.exe`, the Start menu, search, notifications) that aren't app windows, i.e. the taskbar (a click on the tray icon focuses it before the panel opens: before, that switched to the global push-to-talk keys), Alt+Tab's switcher and the desktop. File Explorer's windows count as an app. `TestShellKeepsApp` checks the taskbar and the switcher. Each new app is reported (`ActionApp`).
- **Push-to-talk follows the app** (`App.fgApp`, from `ActionApp`): `pttCombos` are the foreground app's keys. While keys are held, a switch releases only the keys the new app doesn't use and presses its new ones (`syncPTTKeys`), with the hand-over loan taken back first; a key both use never bounces. An app with push-to-talk off releases them until another app comes to the front. Changing keys while held switches the same way. The flow's badge names the combinations held ("Holding Pause · Mouse 4").
- **One key, one job** (`keyConflict`): wherever a combination applies (its app; for a global key, also every app that keeps the global keys of that function), it is in one list only and never a push-to-talk key Resound presses there (which would trigger itself). The overlay's key counts in every app. An app may take a key of the global list it shows as its own.
- **Which apps run** (`input.RunningApps`, a Toolhelp snapshot, ~1 ms, off the UI thread) is read when the panel opens, an app page opens, an app comes to the front, or apps with overrides come or go. While an app with an override runs, the home page's status reads "Ready · Valorant keybinds" (or "Keybinds for 2 apps"): its keys apply while it is in front. The list of apps to add (`input.WindowApps`: programs with a visible, titled, unowned, uncloaked top-level window that isn't a tool window, without Resound and parts of Windows' shell) is read when the Keybinds page opens.
- **The panel** (Settings → Keybinds): a `ui.Keybind` card per function under "Global" (a short line under each section caption, an info icon per function and option; the header's Help button, `ui.HeaderButton`, opens the article), then "App keybinds": a Nav per app (what it replaces) and a dropdown of running apps to add one, which opens its page; then the options (`ui.ToggleInfo`). An app's page has the same cards for it: the global keys it keeps are shown muted with a "Global" caption, + gives it keys of its own, ⊘ (left of +) turns the function off there (None, also in the list while recording), ↺ goes back to the global keys, a trash button in the header removes the app after a confirmation. Recording shows what was pressed, a hint, and a list of ready-made keys (`input.Presets`; an app's starts with None). Why a key wasn't taken shows on its card. The push-to-talk card has a keyboard tool that presses its keys after 5 s ("send to game"), counting down on the card. The guided setup's push-to-talk step and the overlay page use the same card.

## In-game overlay

`app/overlay.go`, `ui/overlay.go` (geometry, tested), `ui/overlay_windows.go` (window, frames, animation), `ui/d2d_windows.go`, `input/hotkeys.go` (`Filter`). One key (`overlayKeys` in `config.json`; none = off) slides a bar of the favorites in at the left (default) or right edge of the primary screen (`overlayRight`). The wheel moves the highlight and stops at the ends; the key again plays the highlighted sound for everyone (`App.playSound`, shared with the phone), Esc closes it on its release. Holding Esc for 700 ms (`input.EscHoldTime`) closes it and stops all sounds; the bar turns red meanwhile (slowly at first, so a tap barely tints it). Nothing else closes it. The highlight comes back where it was left (`overlayLast`), so a sound can be picked ahead and played later with two presses; the first time it starts in the middle.

- **Never takes the focus.** A layered window (per-pixel alpha via `UpdateLayeredWindow`), topmost, a tool window, never activated (`WS_EX_NOACTIVATE`, shown with `SW_SHOWNOACTIVATE`) and transparent to the mouse, so clicks reach the game. It re-asserts topmost each time it opens. It is clipped to the primary screen throughout (`overlayPlacement`, drawn with `UpdateLayeredWindow`'s source offset and size), so nothing shows on a screen beside it: it slides in from the very edge, its bar starting flush with the screen's edge, moving 20 px inwards while it fades in. It showed over every game tried, windowed and fullscreen (Windows presents most fullscreen games like borderless windows); a game in true exclusive fullscreen would cover it. Checked with `TestOverlayLive` (opt-in): the foreground window doesn't change.
- **Input.** Its key, and Esc and the wheel while it is open, are swallowed in the low-level hooks (returning 1), which keeps them from every program, raw input included; everything else passes. `input.Filter` decides inside the hook callback (Windows needs the answer at once) and so keeps whether the overlay is open itself, and the hook thread times Esc being held (a thread timer, not key repeats, whose timing is a user setting); the app follows its events and tells it about opening and closing from the panel (`Watcher.SetOverlayOpen`). A swallowed press has its repeats and release swallowed too; of a combination only the completing key is. The mouse hook (`WH_MOUSE_LL`) is installed only while the overlay is open; precise wheels' small deltas add up to whole notches. While a key is recorded in the panel, the overlay key isn't taken, so it can be recorded again. Checked with `TestOverlayHookLive` (opt-in): an observer hook behind the watcher's never sees what it swallows. Games running as administrator don't receive the hooks (as with all hotkeys). The key can be a mouse button (3–5), alone or with keys; its press and release are swallowed in the mouse hook like a key's.
- **Look.** A capsule bar (dark, 96% opaque) of round buttons in the phone's card colours (a little lighter), each with its emoji or the first two letters of its name. The highlighted one is a pill reaching towards the screen's middle with the name beside the icon (its first 16 characters, then "â€¦"); moving the highlight redraws it at once, without animation. Favorites follow the phone's Favorites order; more than fit in 70% of the screen height scroll, the highlight kept in the middle, the cut-off ends fading into the bar. Without favorites, a pill says how to add some. Sliding in takes 130 ms, out 100 ms (with a fade); playing flashes the pill green (red if the sound can't play) for 150 ms first. A wide drop shadow (the panel's blur, 64 px with a 14 px spread, its darkest point capped at 50%) lies beneath bar and pill and sets them apart from any scene without blacking it out; the panel's picture of it has a modest one.
- **Drawing.** GDI can't draw per-pixel alpha text or color emoji, so the overlay uses Direct2D (a DC render target on a premultiplied DIB, at 96 DPI so a DIP is a pixel) and DirectWrite, called through their COM vtables without cgo (`comObj.call`, marked `//go:uintptrescapes` like `LazyProc.Call`, so locals passed by address can't move with a growing stack). Emoji come out in Windows' own (Fluent) style. The render target is software: a hardware one copies each frame back from the GPU (4.8 ms a frame instead of 2.7 at 150%). The buttons are drawn once per list into a cached layer (laying out emoji was most of a frame's work), and the blurred shadow masks are cached. Sliding only moves and fades the window; frames are drawn again only when the highlight moves or flashes, and while Esc is held.
- **Panel.** Settings â†’ In-game overlay: the key (a `ui.Keybind` card, as on the Keybinds page; removing the key turns the overlay off), the screen edge (an outlined Left/Right group, `ui.Segmented`, greyed out while no key is set anywhere), below the key a note naming the apps with an overlay setting of their own and a link to App keybinds (`ui.ParagraphLink`; an app's own key or None replaces the global key while it is in front, and the open overlay closes when an app without a key comes to the front), a Show/Hide button to try it without a game (Esc and the wheel work as in a game, the hook running just for it if no key is set). The page shows a small, fixed picture of it (`ui.OverlayPreview`, the same renderer at 55%, six example buttons with colours and emoji, the highlighted one saying SCROLL between arrows) with how to use it in a column beside it, from the top of the page, the key's first mention underlined.

## Routing (Windows side of VB-Cable)

- **The model.** The game's mic is "CABLE Output". Resound plays into "CABLE Input". The real mic reaches the cable through Windows' "Listen to this device" with "Playback through" = CABLE Input.
- **Undocumented properties.** "Listen" is stored in two properties of the capture endpoint, `{24dbb0fc-9311-4b3d-9cf0-18ff155639d4}`, pid 1 (VT_BOOL) and pid 0 (VT_LPWSTR, a render endpoint ID). Reading them needs no rights; writing needs admin, so the elevated `--apply-routing` helper writes and verifies them.
- **Detection.** VB-Cable is detected by name: render `CABLE Input…`, capture `CABLE Output…`. The 16-channel and A/B variants are ignored. Voicemeeter is detected the same way, by its devices' names (`…Voicemeeter…`, `routing.Status.Voicemeeter`); its settings are never read or changed. The automatic mic choice is the default recording device unless it is CABLE Output, a Voicemeeter device or the apps' microphone of an own routing (muting a mixer's output while sounds play would silence the sounds too).
- **Own routing** (Settings → Audio & voice chat → Advanced, `app.ownRouting`): for users of a virtual mixer such as Voicemeeter, with or without VB-Cable. "Sounds for others play into" (`cableDeviceId`) is an input of the mixer, and "Others' apps listen to" (`appsMicDeviceId`) the mixer's output that games and Discord use as their microphone (e.g. Voicemeeter Out B1). The mixer combines voice and sounds; Resound doesn't route the mic ("Listen to this device" is neither offered nor checked), and the guided setup only shows the routing. The flow's pipes carry info badges ("Via your mixer", "Your mixer"), the "Others hear" card names the apps' microphone, and its meter records it, as it does CABLE Output; until it is chosen, the cable line says "Choose output" and voice chat isn't ready. The Advanced section, after a divider, has a short how-to (a Voicemeeter Banana one when Voicemeeter is installed). Choosing "Automatic: VB-Cable" or "Back to VB-Cable" ends it and clears `appsMicDeviceId`.
- **Warnings** (`ui.Warning`: a yellow outline, a warning icon, one short line, a chevron; the tooltip says more; a click opens a help article, `App.openHelpAt`). Under "Sounds for others play into" while an own routing is on: "Non-standard setup: click for help" → `/help/voicemeeter`. In the setup's audio step while Voicemeeter is installed (and no own routing is set): "Voicemeeter: VB-Cable may break routing" → its "Before you install VB-Cable" section, since installing or connecting a VB-Cable the mixer already uses would break the user's routing. `TestWarningRender` checks the texts fit; `TestAppHelpLinks` (`cmd/webapp`) checks the panel's `help…` links exist. The article's `voicemeeter` visualization draws the Banana setup in Voicemeeter's terms (Hardware Input 1, Voicemeeter AUX, bus buttons A1…B2, B1, Voicemeeter Out B1).

## Installing VB-Cable for the user

"Install VB-Cable" (setup's audio step and Settings → Audio & voice chat; `app/cable.go`, package `vbcable`):

1. **Snapshot** the default playback and recording devices (console and communications roles).
2. **Download** `VBCABLE_Driver_Pack45.zip` from `download.vb-audio.com` over HTTPS (redirects only within vb-audio.com, size-limited) into `%LOCALAPPDATA%\Resound\vbcable\`, and unpack it (flat entries only).
3. **Verify** `VBCABLE_Setup_x64.exe`: a valid Authenticode signature (`WinVerifyTrust`) whose primary signer is VB-Audio's author ("BUREL VINCENT …"). Anything else falls back to the manual download.
4. **Record** the pending install (`vbcable-install.json`: start and boot time, the page to return to, the default-device snapshot) *before* the setup runs.
5. **Run** the setup elevated with `-i -h` (silent install). The UAC prompt names VB-Audio as the verified publisher. Windows may also ask "Install this device software?"; that prompt cannot and should not be suppressed. The exit code isn't documented, so success is judged by the devices appearing (polled for 20 s).
6. **Restore defaults.** Windows often makes CABLE Input/Output the default devices when they appear: the user hears nothing, and "System default" outputs and the automatic mic would follow. Each default that moved *to the cable* goes back to the snapshot through `IPolicyConfig::SetDefaultEndpoint`; defaults the user chose are left alone.
7. **Restart.** The panel offers "Restart now": required while the devices are missing, recommended by VB-Audio once they appear ("Not now" then drops the pending state). Before restarting, playback stops, the mic and keys are released and everything is saved. Two ways bring the app back, both with `--resume-setup`:
   - **Restart-apps registration** (fast): `RegisterApplicationRestart`, then `ExitWindowsEx(EWX_REBOOT|EWX_RESTARTAPPS)`. Windows starts the app again at sign-in (expected to be quicker than `RunOnce`; not yet measured), but only if it had been running for at least 60 seconds.
   - **`HKCU\…\RunOnce`** (fallback, registered as soon as the setup finishes): always works, but Windows runs it only after every `Run` entry, one after another, waiting up to ~30 s for each. On a PC with many startup apps that takes minutes (3.5 minutes were measured on a dev PC; the Shell-Core event log, events 9705–9708, shows the order).
8. **Resume.** At start-up (before the outputs open), a pending install from an earlier boot means Windows restarted: defaults are checked again, the state file and `RunOnce` entry are removed (so a fast start isn't followed by a second one minutes later), the panel page is set (the setup's audio step, by name rather than the recorded number, or Audio & voice chat), and a corner notice offers to continue. Without a restart in between, the app only shows "Restart needed" again and re-arms `RunOnce`.

Failures (no network, declined UAC, bad signature) leave the manual "Install manually" path, which works as before. Every start logs its arguments, so `debug.log` shows how the app was started. The guided setup's step is saved in `config.json` (`setupStep`), so any restart continues where the user left it.

**Licensing.** VB-Cable is donationware. VB-Audio's licensing page allows installing the unmodified package from another application, silently, as long as end users can see that it is VB-Audio's product and can donate (mentioning www.vb-cable.com and that it is donationware). Settings → Audio & voice chat therefore shows a credit with links to vb-cable.com and the donation page; the setup's audio step names VB-Audio as VB-Cable's maker and its install button says that installing accepts VB-Audio's license. The pack is downloaded from VB-Audio, never bundled or modified. Professional deployments where users can't donate need purchased licenses, and VB-Cable A+B/C+D may never be bundled. The pack's own readme asks for the author's agreement before integrating it into another installer; see Known issues.

## Importing sounds by drag and drop

The Sound library page lists each library folder and all its subfolders, indented by depth, as drop fields (`ui.FolderDrop`). The subfolders come from the last scan (`Library.Folders`), empty ones included, so a folder structure can be prepared before it holds sounds. Clicking a field opens the folder's sound list below it (see Managing sounds); under the pointer, a small "Show in Explorer" button takes the place of its sound count (a segment of its own, cut out of the field's, since segments are hit-tested in order). A library folder's trash button (as tall as the field, with a tooltip) removes it from the library after a confirmation, leaving it on disk. Above the folders, a short guide (`ui.ImportGuide`) shows a small picture of the gesture: a Myinstants-style button (in the panel's berry red) with its underlined name, the name carried along a dotted path by a hand, and a folder field in its "drop here" look. Two buttons side by side, "Myinstants" and "Sound Buttons World", open `https://www.myinstants.com/` and `https://soundbuttonsworld.com/` in the browser; the panel stays open beside it. The field for adding library folders follows under its own "Add folders" heading. On the home page, the library is the "Folders" card (`ui.PageCards`: two half-width cards, each under its own caption, with the title top left, the status and a chevron at the bottom, a tool button top right and a large, faint filled icon behind the text, clipped to the card). While a card or its tool button is hovered, its status names what a click does: "Import sounds" or "Refresh library" on Folders, "Pair new device" or "Open remote" on Web app. A click opens the library page, and its tool button refreshes. The "Web app" card beside it, under "Remote", opens the Remote App page. The library page's header has a refresh button on its right (`ui.HeaderTool`), like the Folders card's. In the guide's text, "drag its name" is underlined (the row lays its words out itself; GDI's word wrap can't underline part of a paragraph).

- **What can be dropped on a folder** (`app/import.go`):
  - a **Myinstants sound**: its name or its link icon (both link to its `/instant/…/` page), or that page's address;
  - a **Sound Buttons World sound**: its name (a link to its `/sound-button/<slug>` page), or that page's address;
  - any **link to a sound file** (MP3, WAV, FLAC, OGG) or to a **page with exactly one sound**;
  - **sound files** from Explorer or the browser's download list: copied into the folder (the originals stay). Folders dropped there become library folders, as anywhere else on the page.
- **Finding the sound** (`importer.ParsePage`): the page's `og:audio` tag (Myinstants sound pages have it), else its one `<audio>`/`<source>`, `data-url` or link to a sound file. Pages with several are refused; Myinstants search and category pages play from `onclick` handlers and have none, so they get "No sound file found" with a hint to drag one sound. The name is Myinstants' `<h1 id="instant-page-title">`, else `og:title` or `<title>` without the site's suffix, else the file name.
- **Sound Buttons World** (`importer.soundButtonsWorld`) is an Angular app whose pages have no audio link: its Download button is a script. Each page carries Angular's server state (`<script id="serverApp-state">`, JSON with `&q;`-style escapes), where the button sits under its API request, `/api/memes/button?url=<slug>`, with its `name` and `fileName`; the site plays it from `/uploads/<fileName>` on its own host (seen in its bundle and checked live). So when a page has no other sound, the state is read: the entry for the page's own slug (else the page's only button entry), a plain file name of a sound type, its name as the sound's name. Related buttons and the lists on search and category pages are never taken, so those pages give "No sound file found".
- **Downloading** (`importer.Fetcher`): HTTP(S) only. The dialer refuses loopback, private, link-local and CGNAT addresses after name resolution (redirects included), so a link can't reach this PC or the LAN. Pages are read up to 2 MB, sounds up to 25 MB, 30 s in all. A sound needs an audio Content-Type of a supported format, or the right extension with a generic type. It is written to `~resound-*.<ext>` in the target folder (the library ignores it), checked by decoding its first half second (`audio.CheckFile`), and only then given its final name.
- **Names** (`importer.SanitizeName`): characters Windows forbids, control and invisible format characters are removed, spaces collapsed, trailing dots and spaces dropped, reserved device names (CON, NUL, COM1, …) get a `_`, at most 80 characters. An existing file is never replaced: `Name (2).mp3`, … (a hard link claims the name first).
- **Already in the library?** Right after the download, `Library.Duplicates` looks for present sounds with the same content: the fingerprint (as for moved files), among files of the same size, hashing those the indexer hasn't reached yet. A match doesn't stop the import; the card says where the sound already is. Sound files copied from Explorer are checked the same way, and the note after copying says how many were known. Names never collide: a second "Horn" becomes "Horn (2)", as in Windows.
- **The card.** Once saved, a card under the folder shows the duplicate warning (if any), a name field (`ui.TextField`) pre-filled with the page's name and selected, and three buttons: **Discard** stops the preview and deletes the file (retrying while the decoder closes it); **Preview** plays it on "You hear" only, from the start, and turns into **Stop** while it plays (back to Preview when it ends: `importPreviewEnded` on the engine's finished event); **Save** (or Enter) renames the file to the typed name; Esc keeps the page's name. The sound is in the library either way until it is discarded; a rename is picked up like any rename. A newer import closes the previous card, keeping its name.
- **The folder's field shows the import.** While a download runs and while the card is open, the field's folder icon and frame take the accent colour, its sound count gives way to "Downloading…" or "Name the new sound", and the field and its card share a lighter band (`ui.GroupStart`/`GroupEnd`), so the card visibly belongs to that folder; afterwards it reads "Added “Name”" (or "Discarded “Name”") for 3 seconds, so no list of past imports grows on the page. Failures show under the folder as a message (no sound at this link, several sounds, unsupported format, too large, a local address) for 8 seconds. A link dropped outside the folder fields asks, for as long, to drop it onto a folder. Running downloads continue when the panel closes; a sound that finishes while it is closed keeps the page's name.
- **Licensing.** Myinstants' sounds are uploaded by its users, and many are clips of copyrighted material; its terms allow personal, non-commercial use. Resound only downloads what the user drags in, one sound at a time, like a browser download. It doesn't search, list or scrape Myinstants.

## Cutting sounds in the editor

Files Resound can't play, videos (MP4, MKV, WEBM, MOV, …) and audio in other formats (M4A, AAC, OPUS, WMA, AIFF, …; `editbridge.Editable`), dropped onto a folder field, open in [audiocutter.online](https://audiocutter.online), a browser audio editor that decodes them with FFmpeg in the browser. Resound doesn't embed the editor: the panel has no web view, so the app's edit page (`webapp/src/edit.html`, `/edit`) hosts it in an iframe, in a browser window of its own.

- **The handoff** (`app/edit.go`, `editbridge`, `js/edit.js`):
  1. The drop registers the file with `editbridge.Bridge` (a random 128-bit token) and starts its HTTP server on `127.0.0.1`, on a free port, if it isn't running. The panel opens `<app>/edit#v=1&p=<port>&t=<token>` in Edge's app mode (1280×860), else in the default browser, like the remote on this PC.
  2. **Consent, once per browser.** Before anything reaches Resound (the first request is what makes the browser ask for Local Network Access), the page explains what the editor is: audiocutter.online, a third party's editor, loaded from its site, working on the file locally. **More info** opens the help article (`/help/audio-editor`, a new tab); **Accept and open the editor** (focused) stores `resound.editorConsent` in `localStorage` and goes on. The page's `close` signal waits for it too. Measured: no request to `127.0.0.1` before the click, a second visit goes straight on.
  3. The page moves port and token from the fragment into the tab's `sessionStorage` and out of the address bar, reads the file's details (`GET /v1/<token>`: name, folder name, size, type) and the file (`GET …/source`), and only then embeds `audiocutter.online/import/`, whose import page gives up 30 s after saying it's ready.
  4. On the editor's `ready`, the page posts a session (`{type: 'session', manifest}`, the postMessage API): the file as a `File`, one fragment covering it, a banner ("Cut a sound for Resound", the instruction, the Resound logo as a `data:` URL drawn from the page's own copy, so the editor never fetches it from the host), "Add to Resound" as the submit label, an accent (banner tint, submit button; the editor makes the button's text white), and `output: {mode: 'postmessage', format: 'flac', targetOrigin}`. These five `session.ui` fields are all the branding the editor takes (its schema drops other keys; no message or URL parameter sets its theme); it follows the system's light or dark theme and remembers its own toggle. Its dark theme can't be chosen from outside: `color-scheme: dark` on the iframe doesn't change the frame's `prefers-color-scheme` in Edge (measured), and the theme it remembers is in its own storage. While editing, the page's own bar shrinks to a status line; clips added show as chips on its right, the newest filled and scrolled into view, older ones fading out at the left edge, without a scrollbar. Only messages from the editor's origin and frame count.
  5. Each "Add to Resound" posts the rendered FLAC back to the page (`result`), which sends it to `POST …/result`. Resound saves it like a download (`importer.Save`: `~resound-*.flac`, `audio.CheckFile`, the edited file's name made unique, at most 100 MB), looks for duplicates, and shows the usual naming card under the folder. Clips are independent imports, so one video gives as many sounds as the user adds; the page lists them in its bar.
  6. **Finishing closes the window.** **Done** in the page's bar ends editing; so does saving a sound of the library (the window closes 2.5 s after "Saved", unless **Keep editing** is pressed), and **Stop editing** under the folder (the page checks `GET …/state` every second and finishes). The page sends `POST …/done`: the file goes at once (no grace) and Resound closes the window.
     - **Why Resound closes it.** A page may only close a window that a script opened, or one whose history holds a single entry. The edit page starts with one (it replaces its fragment), but the editor's import page stores the session and moves on to its editing page inside the frame, which adds a second: measured in an Edge app window, `history.length` goes from 1 to 2 and `window.close()` is refused ("Scripts may close only the windows that were opened by them"). Opening the page from a script instead would need a popup, which browsers block without a click.
     - **Which window.** Just before `done`, the page sets its title to `Resound · Closing <16 random hex digits>` and sends it along (`editbridge` refuses other titles). Resound (`ui.CloseBrowserWindow`) posts `WM_CLOSE` to every visible `Chrome_WidgetWin_1` window titled exactly that, retrying for up to 2 s while the browser takes the new title. An Edge app window's title is the page's title alone; a normal browser window's adds the profile and browser ("… - Personal - Microsoft Edge"), so a window with other tabs never matches. Measured: the app window closes 0.3 s after Done; in a normal tab beside another, nothing closes, and after 2.5 s the page restores its title and says it can be closed.
     - **Stop editing** (`Bridge.Stop`) leaves the file in a stopped state: only `state` and `done` are answered, and it goes after 5 s if no page finishes it (closed already). The panel drops it from the folder at once.
     - Otherwise the page's `pagehide` sends `POST …/close` (`keepalive`). A page that doesn't load the file again within 10 s (a reload does) counts as closed: the file is no longer served, and the server stops with the last file. The editor's own Download button still works.
     - Checked end to end in an Edge app window against the live editor (`cmd/devedit`, whose Enter is Stop editing): Done after a clip, a saved sound, Keep editing, Stop editing, and Done in a normal tab.
- **The folder's field** says "Opening the editor…", then "Editing in your browser…" (accent, like a download), with a line about adding clips and two buttons, **Show editor** (opens the page again; both windows work) and **Stop editing**. While files only the editor takes are dragged over a folder, it reads "Drop to cut in the editor" (`FolderSpec.DropHint`, from the drag's data in `rowState.dragged`). At most 3 files open per drop, up to 1 GB each (the editor reads a file into memory whole). Files open in the editor survive the panel closing and the list of finished imports being trimmed.
- **Security of the server.** Bound to `127.0.0.1` (no firewall prompt), alive only while files are open. A request must name the server's own `Host` (against DNS rebinding), come from the app's origin (`Origin` must be `appOrigin(appURL)`, e.g. `https://getresound.app`; requests without one are refused, and refusals carry no CORS headers) and carry a known token. Responses are `no-store`; preflights allow `Content-Type` and answer Private Network Access's `Access-Control-Request-Private-Network`.
- **Privacy: the host learns nothing.** The token and port travel in the fragment, which browsers never send; the page names no file in its title (history). Its own Content-Security-Policy (a `<meta>` tag; `_headers` drops the site-wide header for `/edit`, which would apply on top, and sets `X-Frame-Options: DENY` in place of `frame-ancestors`) allows `connect-src http://127.0.0.1:*` and `frame-src https://audiocutter.online` and nothing else, not even `'self'`: once loaded, the page can't contact its host. `TestEditPagePrivate` (`cmd/webapp`) pins this. Measured with Playwright and Edge (`cmd/devedit`, an MP4 and an OPUS file, two clips each): the app's host got the page, its stylesheet, script and logo, nothing else; audiocutter.online and `unpkg.com` (its FFmpeg core) got only GETs, no audio.
- **Local Network Access.** Chrome 142+ (and so Edge) asks once per site before a public site reaches `127.0.0.1`: "getresound.app wants to access apps on this device". The page says so before connecting. A failed request can't tell a closed Resound from a refusal, so the page asks `navigator.permissions` and, when the permission is denied, says how to allow it. Simulated with `--ip-address-space-overrides=127.0.0.1:8095=public`: denied → the page's explanation, granted → the editor.
- **Resound's colours in the editor.** The editor is another origin: no stylesheet of ours reaches into it, and Edge doesn't apply SVG reference filters (`filter: url(#…)`) to a cross-origin frame either, not even through a wrapper (measured: our own bar took the same filter). CSS filter functions do apply, so the frame gets one chain (`LOOK` in `edit.js`): `hue-rotate(-72deg) invert(1) sepia(0.064) hue-rotate(19deg) invert(1) contrast(1.072)`. The hue rotation turns the editor's single control colour, `--primary`, Tailwind's blue-600 (`#155dfc`), into a teal green. The invert–sepia–invert sandwich tints dark greys cool and fades out towards black and white, which stay exact; the inner rotation chooses the tint's direction. The contrast takes the darks a step further down. The numbers were fitted against the editor's dark greys (sampled: page `#262626`, panels `#353535`, borders `#404040`, controls `#4a4a4a`) and Resound's (`#1c1d22`, `#2a2c33`, `#33353c`, `#3a3d46`), weighted on the page, while keeping the blue on the green that `hue-rotate(-60deg)` alone gave. Measured in Edge: page `#1c1c21`, panels `#2c2c31`, buttons `#00876e` (hue 169°, before `#008b70`, 168°; white text 4.4:1); light mode's page becomes `#eeeced`. The accent is set to the same blue, so "Add to Resound" matches the other buttons; the logo is drawn rotated back by the hue first. Other colours shift too (red warnings purple), and ClearType's colour fringes on text become magenta/green instead of red/blue (as strong as before). Should the editor change its blue or greys, `LOOK` needs refitting.
- **Why FLAC.** The editor renders at the sample rate it guesses from the file's first 64 KB: WAV, AIFF, FLAC and OGG headers, else the first byte pair that looks like an MP3 frame sync, which inside a video container is chance (measured: MP4 → 32 kHz, MKV → 11.025 kHz, WEBM → 48 kHz). MP3 below 32 kHz is MPEG-2/2.5, which Resound's MP3 decoder (go-mp3, MPEG-1 only) can't read, so such clips were refused; FLAC decodes at every rate and doesn't add a second lossy encoding. The low rates themselves are the editor's to fix.
- **Audio tracks.** The editor has no track choice: no manifest field, no UI. It takes the first audio track (native `decodeAudioData`, or FFmpeg `-map 0:a:0?` when extracting from MP4/MOV/WEBM), and for other containers FFmpeg's default stream; with a two-track MP4, MKV and WEBM the first track came back each time.
- **The page's layout.** The editor's page is always taller than its frame: its session banner (53 px) sits above an area with `min-height: 100%`, so it scrolls by the banner's height (+20 px) whatever the frame's size, over empty space. The frame doesn't scroll (`scrolling="no"`, which only takes effect when set before it loads) and is at least 480 px tall, enough for the editor's controls; in a shorter window the page itself scrolls under its sticky bar, with the site's scrollbar (`scrollbar.css`). The wheel over the frame stays with the editor (its root has `overscroll-behavior: none`, which stops scroll chaining to our page); over the bar, and the scrollbar, scroll the page.
- **Editing a sound of the library** (the scissors in a folder's sound list, `App.editSound`): `Bridge.Add(path, dir, replace)` with replace; the page reads `replace` and `name` from the file's details and says "Edit a sound for Resound" and "Save to Resound". The editor's saves come back in the sound's own format (it reads MP3, WAV, FLAC and OGG headers right, so their sample rate is the file's) and replace it (`App.replaceSound`: a checked temporary file, the sound stopped where it plays, then renamed over it), so the sound keeps its path and with it its ID and settings; the scan measures it again. A sound open in the editor shows "Editing…" in place of its tools; its scissors bring its editor back.
- **Esc.** The panel's Esc hook also sees Esc pressed in the browser, where users press it while editing; with a file open in the editor, Esc on the library page does nothing (`App.onEscape`), and the hook never swallows it, so the editor still gets it.
- **The editor's API** (verified in its live bundle, Oct 2026): the docs disagree with each other (the hosted-sessions page calls inbound postMessage sessions future work); the import page answers `ready` with `capabilities: ['audio', 'session']`, rejects a bad manifest with `{type: 'error', issues}`, and loads session files through the same decoder as a dropped file (native decoding, then FFmpeg), so a video works when its file name has its extension.

## Managing sounds

On the library page, clicking a folder's field opens a list of the sounds directly in it (`app/sounds.go`), below the field and indented one level deeper; its subfolders keep their own fields, with their own lists. The folder's icon is an open folder meanwhile. The open folders are kept while the app runs (`soundLists`, by lower-case path), also when the panel closes. A list is sorted by name; an empty folder says so. Each sound (`ui.SoundItem`) has three small tools, which brighten while the pointer is on its line:

- **Scissors**: edit it in the editor, where saving replaces it (see Cutting sounds in the editor).
- **Pencil**: a name field in its place, filled with the name; Enter or Rename takes the typed name (cleaned as for downloads, `importer.SanitizeName`; refused when another file has it), Esc or Cancel keeps the old one. The file is renamed in its folder, with its extension; the scan matches it by its NTFS file ID, so it keeps its settings.
- **Trash**: a confirmation dialog (`ui.Confirm`, on its own goroutine), then the file goes to the Recycle Bin (`ui.RecycleFile`, `SHFileOperationW` with undo, without the shell's own dialogs). Its record stays for 30 days as a tombstone, so restoring the file restores its settings.

Before a rename, a replace or a deletion the sound stops wherever it plays (`App.stopSound`, by the voices' sound ID), and the file operation retries while the decoder lets go of it. Afterwards the library is scanned, phones are told (`libraryChanged`), and the folder's field says "Renamed to “…”", "Updated “…”" or "Deleted “…”" for a moment; a failure shows under the folder.

## Library and IDs

- Each configured folder becomes a tab, plus one tab per subfolder that contains sounds, at any depth down to `MaxDepth` (8) levels, depth first in name order. Direct subfolders are named as before ("Anime"), deeper ones by their path below the library folder ("Anime › Naruto"). Sounds are listed newest first.
- The scan skips folders whose names start with `.` or `$`, links and junctions (no loops), and files named `~resound-*` (downloads in progress); it visits at most 5000 folders. It also records every subfolder, empty or not (`Library.Folders`), for the panel.
- **Notes** about the library (what a refresh found, added folders, copied sounds) show on the library and home pages for 5 seconds (`setLibNote`); a newer note replaces an older one and its timer.
- **Library folders** are what the user added (`config.json`). A folder inside one is already covered and isn't added again; adding a folder that contains library folders replaces them with it. "Refresh" (library page or home page) first removes library folders that no longer exist (moved, renamed or deleted in Explorer; a folder that only can't be read stays), then rescans everything, so new subfolders, nested structures and moved files are picked up, with the usual matching below.
- **Stable IDs.** A sound or tab gets its ID when first seen and keeps it. New IDs are the 53-bit FNV-1a hash of the lower-cased path (as before, so phones from earlier versions keep working); they are exact in JavaScript.
- **Matching on scan** (`reconcile.go`), cheapest first:
  1. same path: unchanged, or edited in place (size or time differs: fingerprint and length cleared, read again);
  2. NTFS file ID (volume serial + file index) of a record whose path vanished: renamed or moved on the same drive, without reading the file;
  3. fingerprint of such a record, only tried when one has the same size: moved across drives;
  4. otherwise a new sound. Copies stay separate sounds, because only vanished records can be claimed.
  - A folder that vanished hands its tab ID to the new folder that at least half of its sounds moved to (a renamed folder keeps its phone layout).
- **Tombstones.** Records of missing files and folders are kept for 30 days (`missingSince`), so removing and re-adding a folder, or moving a file out and back, restores its settings.
- **Index file.** `library.json` holds the records (with their measured `level`: loudness, robust peak and measurement version), settings (favorite, volumes, phone color and emoji) and phone layouts (mode, sorting and custom orders by sound ID, and the tab order, `tabOrder`). It is written atomically by a single debounced saver; an unreadable file is moved aside, never overwritten. `sounds.json` from earlier versions is migrated on first start and renamed to `sounds.json.migrated`.
- **Indexer.** A background worker reads new and changed files in two stages. First, one at a time and without decoding audio:
  - a **fingerprint**: SHA-256 (first 128 bits) over the size, the first 64 KB and the last 64 KB, so at most 128 KB per file;
  - the **length** from the headers (`audio.ProbeDuration`): WAV/FLAC/OGG headers; for MP3 the Xing/Info or VBRI frame count, or the bit rate for constant-bit-rate files (an estimate for VBR files without a VBR header, corrected after the first full play).
  - then the **loudness** (`audio.MeasureLoudness`, see Loudness normalization), on up to 4 workers (half the CPU's threads). Decoding to the end also gives the exact length. Levels from another `LoudnessVersion` are measured again; a file that can't be decoded is tried again when it changes. Edits clear the level like the fingerprint; moves and renames keep it.
  - Progress shows in the panel; sounds are playable before they are indexed.
- `GET /api/tabs` and `GET /api/library` rescan when the last scan is more than 5 s old.
- **Tab order** (`taborder.go`). The phone can arrange its tabs; the panel keeps the folder order (`Tabs`), the API sends the phone's (`PhoneTabs`). The stored order holds every known tab where the phone shows it:
  - new tabs (an added folder or subfolder) are placed by each scan right after the tab before them in folder order, so a new subfolder lands next to its parent or siblings, not at the end;
  - a removed folder's tab leaves the bar but keeps its place while it is tombstoned (30 days), so adding the folder back (or moving it out and back) returns it there; renamed folders keep their tab ID and so their place; expired tombstones leave the order;
  - an arrangement saved by a phone that lacks some tabs (removed, or new and not seen yet) keeps those after the tab they followed so far. Unknown and repeated IDs are ignored.
  - Resetting all colours and layouts on the phone also resets the tab order.

## The app and its connection

The phone remote is a web app on an HTTPS host (`webapp/`, built by `cmd/webapp`, hosted at `https://getresound.app` on Cloudflare Pages; nothing of it is in the exe). Being a secure context, it can be installed, keep the screen on and start offline. It connects to the PC with a **WebRTC data channel, without a signaling server**, the technique of libp2p's "WebRTC Direct" (`server/rtc.go`, `webapp/src/js/rtc.js`). The PC runs no web server for it (only a loopback one while a file is open in the editor, see Cutting sounds in the editor).

- **Pairing QR code:** `<app>/#pair&v=1&a=<IPs>&p=<port>&f=<certificate fingerprint>&c=<pairing code>&n=<PC name>`. Everything after `#` stays in the browser; the host never sees it. The Remote App page's "Copy link" button puts the same link on the clipboard (`ui.SetClipboardText`, `CF_UNICODETEXT`), to open on another device or in a development build of the app; the button reads "Link copied" for 2 s. The link holds the pairing code, so it is never logged.
  - **Addresses.** `LocalAddresses` ranks private addresses of physical adapters first and labels each adapter ("Ethernet", "Wi-Fi", "WSL", "Hyper-V", "VPN", …); virtual adapters and public addresses are marked `Other`. The code carries up to three, `Other` ones only when there is nothing else, and the app tries them all.
  - **Codes** are single-use and valid for 10 minutes; the panel shows a fresh one after each pairing. A device that is paired with this PC already (same certificate fingerprint) keeps its pairing when it opens a pairing link, leaves the code unused and takes the link's addresses, so scanning again also fixes a changed IP address.
- **The app writes both sides.** It creates its offer as usual, then sets an answer it built itself: the PC is an ICE-lite agent at the QR code's addresses (UDP, `serverPort`, 8080 by default), with the PC's DTLS fingerprint and ICE credentials the app picks:
  - pairing: ufrag `p`+nonce, password derived from the pairing code (`pairPassword`);
  - a paired device: ufrag `d`+device ID+nonce, password = the device key (HMAC of `deviceSecret` and the ID).
- **The PC** reads the socket under pion's UDP mux (`rtcConn`). The first STUN check with an unknown ufrag is verified (MESSAGE-INTEGRITY with that password) before anything is set up; then a pion peer connection is created with the same credentials and a made-up offer carrying the app's ufrag, and the mux delivers the check to it. Wrong or outdated keys get no answer at all.
- **Trust.** DTLS authenticates the PC to the app (fingerprint from the QR code). The app's certificate isn't checked; the app authenticates with its first message: `hello` with its key, or `pair` with the code (answered by `welcome` with a new device ID and key). Devices expire after 180 days without use; keys and codes are never logged.
- **Certificate.** ECDSA P-256, self-signed, 30 years, created once and kept in `remote.json` (`rtcCert`), so the fingerprint in paired phones stays valid. "Sign out all devices" replaces `deviceSecret` and so every device key; the certificate stays. The Remote App page lists the paired devices, newest use first, named from the user agent sent at pairing (`server.DescribeAgent`: "Chrome on Android", "Safari on iPhone"), with when each was last used (or "Connected now") and paired, and a small Remove button. Removing one (`Server.SignOut`) forgets it and, like signing out all (`Server.SignOutAll`), closes its open connections at once: a session is authenticated only by its hello, so it would otherwise keep working until it reconnected. Its next hello is denied (`TestRTCSignOutClosesConnection`).
- **Protocol** (version 1): JSON text messages; anything longer than 16 KiB is split into frames starting with `+`, the last one with `.`. `req` (method, path, headers, body) is an HTTP request served by `Server.Handler`, marked with the device, and comes back as `res` (status, `Content-Type`, `ETag`, body); requests without a device are refused. So the remote speaks a REST API: `rtc.js` replaces `fetch()` for `/api/` and reconnects when needed. A failed connection looks like a failed fetch, and the remote's own retry logic takes over.
  - **Events** go the other way, unasked: `{"t":"event","e":<name>,…}` to every signed-in connection (`RTC.broadcast`; connections still pairing get none). `rtc.js` hands them to `resoundRTC.onEvent` listeners. Apps that don't know an event ignore it, so adding one needs no new protocol version.
  - **`library`** (`Server.LibraryChanged`, with `rev`, the library's ETag) says that tabs or sounds changed. The PC sends it once at the end of whatever changed them: Refresh (on the home page or the library page, also when nothing changed, so phones catch up), added or removed folders, a finished import (the name kept or saved, or the sound discarded), sound files copied in. The remote (`reloadLibrary` in `app.js`) skips an event for the revision it already shows; otherwise it reloads the sound settings (`persistence.sync`), rebuilds the tab bar only when tabs came, went or were renamed (the open tab stays open while it exists), refreshes the open tab's sounds in place from its cache (no placeholder), drops the other tabs' cached lists so they are fetched when next shown, waits for a swipe in progress to end, and tells an open search to reload (`libraryChanged`). Reloads never overlap; an event during one queues one more. Measured with `devremote` and headless Edge: a refresh without changes costs the phone no request; with changes, one each of `/api/library`, `/api/tabs` and the open tab's and its two neighbours' lists.
- **Remote on this PC.** The Web app card's tool button on the home page and the Remote App page open the pairing link in Edge's app mode (a separate phone-sized window), or the default browser without Edge. A browser that is paired already just connects.
- **Measured** (Chrome, Edge 155, Firefox 157 on the dev PC): pairing ~80 ms, reconnecting ~70 ms, an API round trip under 1 ms.
- **Limits.** Phones must be on the same network (no TURN). iOS keeps a home-screen app's storage separate from Safari's, so the connect page has its own QR scanner (BarcodeDetector, else vendored jsQR) to pair inside the installed app. Chrome plans to put WebRTC to local addresses behind its Local Network Access permission; that adds a prompt, nothing else.
- **Older versions** served the remote over plain HTTP with a PIN and cookies. Their `remote.json` fields (`pin`, `sessions`) are dropped on the next save; those phones pair again with the app.

### API

- **Routes:** the 14 Soundux Remote endpoints (`/api/tabs`, `/api/sounds/{id}/play|preview|favorite|volume[/reset]`, `/api/sounds/progress|settings|stop`, `/api/playback/toggle`, `/api/talkthrough/start|stop`, `/api/status`) plus `/api/auth/logout` (the device is signed out).
- **Resound additions:**
  - `GET /api/library`: tabs (with sound IDs in order), sounds (with favorite, custom-volume flag, color, emoji, duration) and layouts in one response. It carries an `ETag` (`"<server start nonce>-<revision>"`) and answers `If-None-Match` with 304, so phones can poll it cheaply.
  - `POST /api/sounds/{id}/appearance` `{color, emoji}`, `POST /api/layouts/{tabId|favorites}` `{mode, sort, orders}`: phone card looks and layouts, stored on the PC and shared by all phones. `sort` (`""` custom order, `name-asc`, `name-desc`) only says how the phone shows the tab: it never changes `orders`, and a body without it keeps the stored one. Colors and emoji are validated because the phone puts them into class names and CSS strings.
  - `POST /api/library/import` `{overwrite, sounds, layouts}` accepts sound IDs or file paths, so settings from earlier phone versions (path-keyed) and exported files can be adopted. Without `overwrite`, only empty values are filled.
  - `POST /api/library/reset-appearance` clears all colors, emoji, layouts and the tab order.
  - `POST /api/library/tab-order` `{order: [tab IDs]}` stores the phone's tab order, answers with the order now shown and sends the `library` event, so other phones follow. `GET /api/tabs` and `GET /api/library` list the tabs in that order.
  - `POST /api/panel/toggle` opens the panel on the PC, or closes it if it is open (`{open}`): a long press on the logo in the phone's bottom bar. The panel is topmost, so it shows above other windows even when Windows keeps the focus with the app in front (it hands the focus over only after the user's own input on the PC). Phones meeting an older PC get 404 and say to update it.
- **Response shapes** match the C++ server, including the volume slider model: −50…+50 makes a sound silent … twice as loud (gain) on both outputs alike, relative to their defaults (`sliderGain`; left of the middle along the volume curve, so −25 is what 50% is to 100%). The Soundux Remote multiplied the volumes, which were linear gains there; on Resound's curve that moved the two outputs by different amounts whenever their defaults differed. The custom volumes are saved as whole percentages; the slider position is read back from the output with the louder default. The default volumes come from atomics set by `applyVolumes`, never a UI-thread round trip that could time out.
- **The slider on the phone** sends one request at a time, the newest position waiting; the last one is sent even after the sheet has closed, and a failed one is sent again once.

- **Arranging tabs** (`tab-order.js`): in edit mode, a long press (600 ms, against accidental reorders) on a tab lifts it (SortableJS, pointer fallback: a copy follows the finger, a dashed slot shows where it lands, the bar scrolls slowly near its ends); dropping it saves the shown order on the PC. One colour can filter it. The tabs are tucked away, and the bottom bar sits on the virtual keyboard: the visual viewport shrinks by its height (`--keyboard`). On Android that shrink leaves out the gesture bar's strip, which the keyboard covers too, so the bottom safe-area inset is added there; on iPhone and iPad it is included already. The two-finger pull arms the search; lifting the fingers opens it and focuses the field (the lift lets a page open the keyboard, and the grid isn't emptied under the fingers before the touch ends). Taps on results keep the keyboard open; scrolling or Enter closes it. Android's Back button closes the search (it adds a history entry).
- **Start tab** (`startTab` in `app.js`). A fresh start opens Favorites, or, with no favorites yet, the library's first tab in the phone's order (Favorites when there are no tabs either), so the app starts on buttons rather than an empty page. The open tab is kept in `sessionStorage` (`resound.openTab`): reloads within the session (an update taking over, coming back from the connect page) return to it; closing the app ends the session. A rebuilt tab bar keeps the open tab while it exists.
- **Cards and layouts** (`createSoundCardElement`, `updateSoundCardDisplay`). Layouts are per tab: 3 columns, 2 columns, or a list. A card is the same element in every layout: it carries its emoji both as `--sound-emoji` (the grid layouts' large emoji behind the name, `::before`) and as a span before the name (the list), and CSS shows the one its grid uses. So swipe previews of tabs in another layout than the live page (`tabs.js`, built before they are attached, so they can't ask their grid) and the sheet's floating copy are right without being rebuilt; before, previews took the live page's layout, and their emoji popped in when a swipe between tabs of different layouts ended. List rows are one line high (`--list-row-height`, long names end in an ellipsis), rounded like the buttons, in the card colour (default rows a little subtler, `--list-surface`), with the playback fill and the brief outline of a new play; emoji, name and the favourite and volume marks share the row's centre line.
- **Card colours** (`styles.css`, `--sound-color-<name>-bg/-progress/-highlight`). Twelve: `default` (no colour), then the hues from `pink` round to `purple` (`pink`, `red`, `orange`, `yellow`, `lime`, `green`, `teal`, `sky`, `blue`, `purple`), then `grey` (light grey), so the two greys bracket the grid. The name is what the PC stores (`library.json`, `color`; any `[A-Za-z0-9_-]` name is accepted). The sheet shows them in three rows of four that snake through the hues, the search filter in two rows of six. The in-game overlay has its own shade of each (`internal/ui/overlay.go`). `TestCardColors` (`cmd/webapp`) checks that every colour in the sheet has its styles and is in the search filter, `TestOverlayColorsMatchApp` (`internal/ui`) that the overlay knows it.
- **The sound sheet** (`sound-settings.js`). A long press (or a tap in edit mode) opens it. On phones in portrait it is a bottom sheet, as wide as the screen up to 520 px (like the install sheet); on landscape and wide screens (`(min-aspect-ratio: 1/1) and (min-width: 600px)`, `SIDE_SHEET_QUERY`, the same query in `styles.css`) a side sheet from the right, full height, at most 400 px wide (half the screen on narrow ones), scrolling when its content is taller; a bottom sheet there would be very wide and leave little room above it. A copy of the button floats in the space beside the sheet (above it, or to its left: `floatArea`), in the page's layout (a list row in the list, at most 520 px wide), and previews on a tap; it moves when the screen turns or the window resizes. Dragging closes the sheet: down for the bottom sheet, right for the side sheet, whose vertical moves scroll it (`touch-action: pan-y`, so a sideways move over its controls is never the browser's swipe back). Esc closes it too (the emoji picker first). Its sections: favourite and preview, **Custom Button Volume** (−50…+50; the (i) after the title opens a popover saying it only scales this button, for both outputs), **Button Color**, **Button Emoji** (tapping the current emoji opens the picker to change it).
- **Platform features:**
  - **Keep the screen on** (`screen-wake.js`): the Screen Wake Lock API, on by default, requested again whenever the app becomes visible (browsers drop it in the background), and retried on the next tap where a browser wants one first.
  - **Fullscreen:** the installed app opens fullscreen (`display_override` in `manifest.json`; iOS falls back to standalone). In a browser tab, the "Fullscreen" setting enters fullscreen with a tap, which browsers require (`fullscreen.js`); the setting is hidden where the app is fullscreen already or the browser can't.
  - **Vibration** on play and stop (`device.js`, Vibration API: Android), "Vibrate on Tap", shown only where the browser offers it.
  - **Install:** on the remote, an "Install app" pill in the top bar opens a sheet with why (home screen, the whole screen, never lost among tabs) and how (`install.js`). Browsers don't report whether a page can be installed, so it goes by browser: Chromium's `beforeinstallprompt` (one tap; never fired once installed, so without it there is no pill), iPhone and iPad (Share → Add to Home Screen, then pairing again in the installed app, which has its own storage), Firefox on Android (menu → Install), Safari on macOS 17+ (File → Add to Dock); nothing in the installed app, apps' built-in browsers or desktop Firefox. "Not now" hides the pill for 30 days; Settings → "Install the app" opens the sheet any time. The connect page offers Chromium's prompt too. `launch_handler` makes a pairing link reuse the open app window; a maskable icon fills Android's icon shapes.
  - **Updates:** `sw.js` caches every file at install (the list and version, a hash of all files, come from `cmd/webapp`), bypassing the HTTP cache, one cache per version, served cache-first: the app starts without the host and a page never mixes two versions. It checks for a new deployment when it comes to the foreground and hourly while it stays there. The new service worker waits until taking over interrupts nobody (`rtc.js`): the app in the background, untouched since it came to the foreground (the usual case, the check takes about a second), or untouched for 30 s with no finger down; never while pairing, whose code works once. Then the page reloads into it. With every window closed, the next start gets it directly.
- **Can't reach the PC.** The PC answers nothing to a device that is on another network, blocked by the firewall, or holds an outdated key or code, so the app can't tell these apart. Once a connection attempt fails (8 s without an answer), the remote covers the sounds with a short checklist, most likely cause first, in the panel's words (`connection-help.js`): Resound running (its Remote App page shows a QR code), the same Wi-Fi (not mobile data, a guest network or a VPN; flagged when the browser reports the device offline or on mobile data), scan the code again (new addresses, outdated key), the firewall ("Allow phones through the firewall", and Windows must treat the network as Private: the rule covers private and domain networks only). It keeps retrying and disappears once connected. The connect page shows the same list when pairing gets no answer, with "use a new code" in place of scanning again.
- **Self-contained.** Every script, style, icon and the emoji data come from the app's own host; the `Content-Security-Policy` in `_headers` (`default-src 'self'`) makes the browser refuse anything else. `TestWebSelfContained` (`cmd/webapp`) fails on any URL in our own files.
- **Icons** are Material Symbols SVGs (`webapp/src/assets/icons/`), painted in the text colour through a CSS mask: `<span class="icon" data-icon="name">`, switched with `el.dataset.icon`. `TestWebIcons` checks that every name used has its SVG and CSS rule.

## UI framework

- **Panel.** The panel is one borderless, DPI-aware popup. Pages are `[]ui.Row` lists **rebuilt from state on every change** (`App.render`). Rows are immutable values implementing `height/segments/paint/click/keepsOpen`.
  - Optional interfaces: `fieldHost` (segments that are dropdown fields; a row may hold several), `tipper` (provides a full-text tooltip), `measurer` (height follows the content, e.g. wrapped text), `segmentKeeper` (per-segment `keepsOpen`), and `dragger` (segments that follow the mouse while the button is held, found again by id after re-renders).
- **Size and shadow.** The panel is 340 logical pixels wide and at least 560 high (`popupMinL`), so switching pages doesn't make it jump. Short pages leave the rest empty, or give it to their first `Flex` row, which keeps the footer after it (Help / Settings / Quit, Continue) at the bottom. Taller pages grow the panel up to 680 (`popupMaxL`, less on small work areas) and then scroll. The drop shadow is a click-through layered window placed directly beneath the panel (`shadow_windows.go`). It shows a blurred, lowered, translucent black rounded rectangle computed in Go (`shadow.go`, three box blurs), so it is equally strong on Windows 10 and 11 and whether or not the panel has focus. `CS_DROPSHADOW` and DWM's frame shadow were too faint.
- **Closing.** The panel stays open when another window gets the focus (clicking elsewhere doesn't close it). It closes deliberately: "✕ CLOSE [ESC]" on its tab, Esc, or the tray icon. Closing keeps the page, so the tray icon reopens it where the user was.
- **The tab** (`paneltab_windows.go`) is a window of its own across the panel's whole top edge, between the panel and its shadow in the z-order, so the panel covers its lower edge and it looks like a card tucked under it. It never takes the focus (`WS_EX_NOACTIVATE`, `MA_NOACTIVATE`).
  - **Stacking.** Shadow, tab and panel own each other in a chain (shadow → tab → panel, set at `CreateWindowEx`), so Windows keeps them in that order and raises them together. Before, the tab and shadow were only placed below the panel when it was laid out; a click that raised the panel left them behind, and another always-on-top window could come between the panel and its tab. `TestPanelMoveLive` checks the order after raising the panel above such a window.
  - **Corners.** Windows 11 rounds the tab like the panel (`DWMWA_WINDOW_CORNER_PREFERENCE`, anti-aliased, the same radius); a window region (`SetWindowRgn`, hard-edged) only where it can't, on Windows 10. 24 px of the tab lie under the panel, more than both corner radii, so its lower corners never show in the panel's rounded top corners. The 1-pixel border Windows 11 draws around rounded windows is translucent by default, which made the panel's sides lighter where the tab lies behind them; the tab gets an opaque border colour instead (`DWMWA_BORDER_COLOR`, `windowBorder`, the grey the default shows on a dark desktop). The panel and the tray menu have no Windows border (`DWMWA_COLOR_NONE`) and paint their own (`canvas.glowBorder`, `borderPixels` in `glow.go`): one pixel of `windowBorder` along the edge, lit towards a light accent near the top left corner by the corner glow's falloff, reaching 30% further along the edges (`borderGlow`, `borderReach`). It follows Windows' rounding (8 logical pixels): only its inner edge is anti-aliased, the outer one is the window's. A Windows border can only be one colour, hence painting it. On Windows 10 (square, no border) nothing is painted.
  - Its labels, icons and the ESC keycap are centred on one line. On the left a six-dot grip and "DRAG TO MOVE" are the handle (a move cursor over it); on the right "✕ CLOSE [ESC]" closes the panel. Both are in a small font (`fontSmall`, 10 px).
- **Position** (`panelpos_windows.go`). By default the panel is docked: centred on the tray icon, against the taskbar on whichever edge it is, above it when the icon is in the lower half of the screen (`dockedPos`). Dragging the handle moves it anywhere:
  - The drag is the app's own, not Windows' move loop (which would move only the tab): the tab captures the mouse, starts moving past the system's drag distance (`SM_CXDRAG`), and moves the panel, tab and shadow together in one `DeferWindowPos` step. Esc during a drag puts it back; losing the capture keeps it where it got to.
  - **Never off screen.** Every placement (each mouse move, every page change, every opening) keeps the panel and its tab inside one screen's work area (`clampPanel`), so no part of it can end up off screen or under the taskbar. While dragging, that is the screen under the mouse; moving onto a screen of another scale or height lays the panel out for it first. A page that makes the panel taller pushes it back up; a shorter one lets it return to its place, since only the position the user chose is saved, not the pushed one.
  - **Kept.** The end of a drag saves the panel's top left corner in screen pixels (`panelPos` in `config.json`, through `Popup.OnMove`). At each placement it counts only while a screen still contains that point (`MonitorFromPoint` with `MONITOR_DEFAULTTONULL`): after a screen was unplugged, or the arrangement or resolution changed so that it is on none, the panel docks at the taskbar, and the saved position comes back with the screen. A new scale or a moved or resized taskbar only clamps it. While the panel is open, `WM_DISPLAYCHANGE`, `WM_DPICHANGED` and `WM_SETTINGCHANGE` (`SPI_SETWORKAREA`) place it again by the same rules (posted, so Windows has finished updating its screens); `WM_DPICHANGED`'s suggested rectangle is ignored, as the panel lays itself out for the scale of the screen it is on.
  - **Reset.** A double-click on the handle, or "Reset panel position" in the tray icon's menu, docks it again and clears `panelPos` (`Popup.ResetPosition`); the menu's button also opens the panel, so the user sees where it went.
  - `TestPanelMoveLive` (opt-in) shows the real panel and drags it past every edge, onto every screen, back with Esc and to a screen that no longer exists, checking that it stays inside a work area with its tab and shadow attached.
- **Tray icon.** A left-click opens or closes the panel. A right-click opens a small menu (`traymenu_windows.go`) with **Show panel** and **Quit** side by side (two thirds and one third), so quitting is one click away whatever page the panel shows, and **Reset panel position** below them (disabled while the panel is docked). It is a window of its own in the panel's look (background, corner glow, `paintButton`, its own drop shadow and rounded corners), always placed like the docked panel: centred on the cursor, next to the taskbar. Unlike the panel it closes like a menu: when it loses the focus (it takes it when it opens, which the shell allows after a click on the icon), on Esc, or after a choice; a right-click on the icon while it is open closes it. Show panel opens the panel, or brings an open one to the front; Quit runs `App.quit`, like the home page's Quit.
- **Esc** goes back a page like the back button (Settings → home), cancels recording a key, and closes the panel only from the home page or the guided setup (`App.onEscape`). It works while the panel is open even if another window has the focus: a low-level keyboard hook (`escape_windows.go`), installed only while the panel is visible, posts a message for Esc pressed elsewhere. It never swallows the key, so the focused app still gets it; with the panel focused, its own `WM_KEYDOWN` handles Esc and the hook stays out.
- **The mouse's back button** goes back a page like the page's back button, but never closes the panel: on pages without one (home, the setup's first page) it does nothing, and an open dropdown list just closes. `DefWindowProc` turns `WM_XBUTTONUP` into `WM_APPCOMMAND` (`APPCOMMAND_BROWSER_BACKWARD`, also sent by mouse software and a keyboard's Back key), which the panel handles by running its header row's back button (`backer`); the tab passes it on. It works while the mouse is over the panel. While a key is being recorded, `OnKey` takes the button first, so it can still be recorded as push-to-talk.
- **Row types:** Brand (logo, letter-spaced title, status), Title, Header (back button), HeaderTool (Header with an icon button on the right), HeaderButton (HeaderTool whose button has a label, e.g. Help), WizardHeader (back button and progress dots), Section, SectionLink (Section with an accent link and its tooltip on the right), GroupStart/GroupEnd (a lighter rounded band behind the rows between them, painted by the popup before the rows), Text, Paragraph (word-wrapped), Flex (fills a short page), DropZone (dashed drop field, clickable), FolderDrop (a folder as a drop field of its own, optionally with an action button, open or closed, with a "Show in Explorer" button under the pointer), SoundItem (a slim line for a sound in an opened folder: speaker, name, small icon tools or a note), TextField (one-line input, below), Button / ClosingButton, Buttons (side by side, each with an optional icon and optionally closing), Nav, NavTool (Nav with an icon button on its left), Radio, Toggle, ToggleInfo (a Toggle with an info icon and its tooltip), Keybind (a function's keys as a card, below), Slider, Stepper, Item, Dropdown, QRCode, Separator, Spacer, and the audio flow's rows (below). Nav tiles are as wide as buttons.
- **Audio flow** (`ui/flow_windows.go`, `app/flow.go`). A diagram of where audio goes, built from four rows that share their column and lane geometry, so the pipes join across row boundaries: the microphone (full-width dropdown with a level bar), the soundboard (test/stop button with a level bar, right column), the cable, and the two outputs side by side. Level bars dock under their dropdown or button as one rounded unit (`paintDocked`, clipped with `canvas.clipRound`). The soundboard plays two streams at once: one into the cable, one to "You hear" (a preview lights only that one), a lane with a jack at each end like the cable. Badge areas are measured with the panel's measuring DC (`Popup.canvas(0)`), so hovering and clicking cover the whole pill. VB-Cable is drawn as a cable whose upper end has two 3.5 mm jacks (`paintJack`: pixel art in device pixels, the same at every scale: a 1-pixel tip, a 6-pixel contact with a divider, a bevelled 5×5 body; pipes and the cable are 3 device pixels wide at every scale to match), one plugged into the bottom of the microphone, one into the left of the soundboard button, whose pipe curves down into the mic's (`paintBend`, an anti-aliased quarter circle drawn per pixel); they join and run down to a third jack at its far end, "Others hear": a fixed card (mic icon, an info icon whose tooltip says to pick "CABLE Output" in games and chat apps, the name), not a choice; the tooltip shows over the mic icon, info icon and name together (`cardLayout`), not only the small info icon, which brightens meanwhile (`TestCableInfoHitArea`). "You hear" is a dropdown. Both have a level bar and a compact volume track with a small speaker icon (Font Awesome's, which stays legible at 10 px where Tabler's outline blurs) at its right end; above 90% (`trackIconFlip`) it moves to the left end, so the knob never covers it (`TestTrackIconClearsKnob`).
  - **Pipes** (`ui.Pipe`) are on, off (dashed), held (dashed: interrupted on purpose, e.g. the mic muted while sounds play, playback paused) or broken (in a warning tone). A connected pipe brightens with the signal passing through it, read on every paint.
  - **Badges** sit on a pipe: an icon on the line and a short label. Hovering shows why; clicking opens the page with the fix, or runs the fix where the flow is next to its controls (the Audio page, the setup's audio step). Broken: mic not routed ("Listen to this device" off or elsewhere), VB-Cable missing or awaiting a restart, an output failed, the chosen mic unplugged. Off: sounds for others chosen to play elsewhere (Advanced). Held: muted for sounds, muted in Windows, paused (phone, talk-through, pause key, the user's own push-to-talk ("You talk"): a pause icon on both of the soundboard's pipes, the label on the headphones' one). Push-to-talk held by Resound shows on the cable pipe.
  - **Badges follow the state.** The pause icon and dashed soundboard pipes show only while sounds are paused (`soundsPaused`); a pause key, the user's push-to-talk or talk-through held with nothing paused (sounds started since play) shows its label on a running pipe. "Holding …" is the keys Resound holds for the app in front; a hand-over or stop key takes them back at once (`reclaimPTT`), so the badge never outlives them. The ticker renders again whenever the holds it shows change (`heldKey`: mic muted by Resound, push-to-talk held, which pause), and the end of playback renders after releasing them; before, the release could come after the last render and leave "Muted for sounds" or "Holding …" on screen.
  - **Mute state.** Resound's own mute while sounds play is recorded in the routing state at once (`setRouteMuted`), and a background routing check that started before such a change is dropped: otherwise a check that read the mic while Resound had muted it would show the mic as muted by the user for up to 3 s after the sounds.
  - **Meters** run only while a page with the flow is on screen and the panel is open: the ticker (`animate`, 33 ms) opens them, takes their peaks with a fall-off of 5 % per tick, repaints, and closes them within a tick of the panel closing. The routing is re-read every 3 s off the UI thread, so changes made in Windows' own dialogs show up.
  - `go test ./internal/ui -run Flow` with `RESOUND_RENDER_DIR` set saves PNGs of the flow in several states (offscreen GDI rendering, no app needed).
- **Icons and images.** SVG icons in `internal/ui/icons/` (Tabler, Font Awesome; added with `scripts/add-icon.ps1`) are embedded and rasterized in pure Go (oksvg/rasterx) as anti-aliased alpha masks at the exact device-pixel size. They are tinted with the row's color and drawn with `AlphaBlend` from a premultiplied 32-bit DIB section, cached per name, size and color. Images (`ui.NewImage`, the logo) are scaled with Catmull-Rom and drawn the same way. GDI's own shapes have no anti-aliasing; text does (ClearType). See `internal/ui/icons/README.md`.
- **Slider.** A thick track with a vertical pill as the knob. − and + move to the previous/next multiple of the step (5% for the volumes); clicking or dragging the track sets the value. The popup captures the mouse while dragging and re-finds the row by id after each re-render. `onChange(value, done)` fires on every move with `done=false` and once with `done=true` on release or a button click, so the app applies volumes live but saves `config.json` once.
- **Pages.** Three layers, each built from shared row builders (`folderRows`, `libraryActions`, `monitorDropdown`, `volumeSliders`, `cableRows`, `pairRows`, …):
  - **Guided setup** (`wizard.go`): shown until `config.SetupComplete`. Welcome, then four skippable steps: sounds; audio and voice chat (the audio flow with the VB-Cable install below it while it's missing, then one button that routes the mic into the cable; "Continue" once voice chat is ready, i.e. VB-Cable installed, sounds into it and the mic routed or none there); push-to-talk key (the global push-to-talk card); phone pairing. Setups in progress from the five-step version are renumbered once at start (`SetupFlow`). Configs from before the setup existed (folders or a cable set) count as complete. Settings → "Run the guided setup again" restarts it.
  - **Home**: everyday use. Logo and status, the status naming apps with keybinds of their own while one runs, problems (failed output, voice chat incomplete), the library tile with a refresh button and what the refresh found (folders are added on the library page), the audio flow, the phone remote, Help (opens the help center, `<app>/help/`, in the browser), Settings and Quit.
  - **Settings**: Audio & voice chat (the audio flow, VB-Cable install and connect, mute-while-playing, a link to the keybinds, restart outputs; under Advanced, where sounds for others play: automatically VB-Cable, or another device for one's own routing such as Voicemeeter, then also the mixer's output others' apps listen to; see Routing), Keybinds (push-to-talk, pause and stop keys, globally and per app; see Keybinds), Sound library, Remote App, App & startup, Backup & restore (one-click backup, Save as…, the backup list, restore from any file, also offered on the setup's welcome page; and a zip of all sound folders, below), and Diagnostics (formats, buffers, latency test, index, server, log/data/program folders). A detail page's back button returns to the page that opened it (a stack, so Settings → Audio → Push-to-talk unwinds).
- **Zipping the sounds** (`app/soundzip.go`, `backup.ZipSounds`). Backup & restore → Sound files puts every library folder into one zip, as the last scan saw it (rescanned when older than 5 s): each library folder is a folder at the zip's top (a second folder of the same name becomes "Name (2)"), with every subfolder the scan found as its own entry, so empty folders are kept, and the sound files at their places. Hidden folders, links, `~resound-*` downloads and files that aren't sounds stay out, as in the library. Before anything is written, a warning gives the number of sounds and their total size (from the index, no disk access); then the save dialog (no start folder, so never the data folder; refused when the drive has too little free space). The zip is written on its own goroutine to `<name>.zip.tmp` and renamed when complete; MP3, OGG and FLAC are stored, WAV deflated. The page shows the percentage and a Cancel button; files that vanished meanwhile are skipped and counted. Quitting or Windows ending the session cancels it and waits up to 3 s for the unfinished file to be removed. The result stays on the page (with "Show in folder") until the next zip. It is never listed or restored: unzipping and adding the folders again does that.
- **Restoring a backup** restarts the app: the running instance would rewrite the config and sound index when it exits, so it starts a new instance with `--restore` and quits. The new instance waits for it, saves the current state as a `…-before-restore.zip`, and replaces the data files. A clean restore also removes data files the backup doesn't contain. Backups are checked first: they need the manifest, may contain only the known files as valid JSON, and are size-limited.
- **Drag and drop** (`droptarget_windows.go`). The popup is an OLE drop target (`RegisterDragDrop`; `IDropTarget` is a static COM object whose vtable holds Go callbacks, which OLE calls on the UI thread from its message loop). So it takes web links from browsers (`UniformResourceLocatorW`, Firefox's `text/x-moz-url`, or plain text that is one http(s) URL) as well as files (`CF_HDROP`). A row implementing `dropper` (FolderDrop) is a drop field of its own: it lights up while something is dragged over it and gets the drop. Elsewhere, the Sound library page and the setup's sounds step accept drops (`Popup.SetAcceptDrops`, `Popup.OnDrop`); without OLE the popup falls back to `DragAcceptFiles` (files only). After a drop the panel asks for the foreground, so a name can be typed at once. The panel stays open while Explorer or the browser has the focus. A folder dropped outside a folder field becomes a library folder, and a dropped sound file adds its folder. Folders that are already in the library, or inside one, are skipped. The folder picker is owned by the panel, so it opens above it.
- **Dialogs from the panel.** Folder and file pickers run from closing buttons; afterwards `reopenPanel` shows the panel again with the result. UAC prompts are not followed by a reopen: activating the popup from the background could fail and leave it open without focus.
- **Dropdown.** The list is an overlay inside the popup, not its own window, so focus never moves and the panel stays open.
  - It opens below or above the field depending on space, as wide as the panel's content even for a half-width field, shows up to 8 items, and scrolls with the wheel or keys.
  - Its `id` re-attaches it to its row after re-renders.
- **Tooltips** appear after 450 ms, only for cut-off text, word-wrapped across the panel width.
- **Key capture.** While the panel has focus, `OnKey` receives keys and mouse buttons 3–5 (over the panel), with left and right modifiers kept separate. Every keybind records the same way: all keys and buttons pressed until the first is let go.
- **Keybind card** (`ui.Keybind`, `keybind_windows.go`): a rounded card with the function's icon, name and info icon, tools on the right (+ add, ⊘ off in this app, ↺ back to the global keys, an optional extra such as send to game, ✕ cancel while recording) and the combinations as chips that wrap, each with its own remove button; it measures its height (`measurer`). Without keys it is greyed out (outlined, muted) and collapses to its header, with no text; an app's card that keeps the global keys shows them as outlined, muted chips under a "Global" caption; None is one muted chip whose ✕ brings the global keys back. While recording, an accent chip shows what was pressed, with a wrapped hint and a dropdown of ready-made keys (a `fieldHost` segment). Notes (a key refused, the hook failing) wrap under the chips. `TestKeybindRender` saves its states.
- **Text field** (`ui.TextField`, `textfield_windows.go`). The row paints the box; a native EDIT control (a child of the popup, which clips children while painting) sits on it, so selection, clipboard, IME and undo work. It is found again by the row's id after each re-render, moved on layout and scroll (hidden when scrolled out), and destroyed when its row is gone. The control is subclassed for Enter and Esc, which post `wmFieldKey` to the popup; the callbacks run from there, since they may remove the field. `Popup.FieldText(id)` reads it for buttons beside it. One field at a time.
- **Dialog** (`ui.Confirm`, `TryConfirm`): ported from the Skira Seed Helper. Input is ignored for the first 400 ms, Cancel is the default, and corner/passive mode shows the hidden-icons hint.

## Install, update, uninstall

- **Install folder:** `%LOCALAPPDATA%\Programs\Resound\Resound.exe`.
- **Registry (HKCU):**
  - `…\Uninstall\Resound` — the Installed-apps entry;
  - `…\Run\Resound` — autostart, only once the user turns it on (guided setup or App & startup); installing doesn't.
  - `…\RunOnce\Resound` — `--resume-setup`, only between a VB-Cable install and the next sign-in.
- **Start Menu shortcut:** `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Resound.lnk`, created through WScript.Shell.
- **Update detection:** a version string in `installed_version.txt`. A different string means an update.
- **Replacing a running exe:** the old one is renamed to `.old`, and a later start deletes it.
- **Uninstall:** the exe deletes itself through a delayed hidden `cmd.exe`.
- **In-app update** (`app/update.go`, package `update`):
  1. **Check.** 10 s after start, then every 12 hours (unless turned off; "Check now" always works): `GET https://api.github.com/repos/motivated2die/resound/releases/latest`. GitHub's "latest" is the newest *published, non-pre-release* release, so drafts and `-rc` releases are never offered; a tag with a pre-release suffix is ignored too. Unauthenticated, GitHub allows 60 requests per hour per IP address, far more than needed.
  2. **Compare.** Semver on the numbers; a full release beats a pre-release or dev build of the same numbers (`0.8.0` > `0.8.0-dev`). A newer release shows a dot and "Update" in the home page's header (next to the version), and "update to vX" on Settings → App & startup.
  3. **Download** ("Update now" on App & startup): `SHA256SUMS.txt`, then `Resound.exe` into `%LOCALAPPDATA%\Resound\update\`, over HTTPS from `github.com`/`*.githubusercontent.com` only (also after redirects), size-limited, with its SHA-256 compared to the sums file.
  4. **Start** the downloaded exe. It is a normal non-portable copy outside the install folder, so `install.Ensure` takes over exactly as for a manual download: it asks this instance to quit (`wmQuitApp`, which releases the mic and keys and saves), replaces the installed exe and starts it with `--welcome=update`. If this instance is still running a minute later, the panel shows an error and the update can be retried. The next start removes the `update\` folder.
  - Development builds check and show updates but don't install them.
  - `RESOUND_UPDATE_API` replaces the API base for tests (`cmd/devupdate`). It must be HTTPS or HTTP to localhost, and assets are then only fetched from that host.
  - The checksum comes from the same release as the exe, so it catches broken downloads, not a compromised GitHub account. Code signing (RELEASING.md) will allow an Authenticode check on top.
- **Portable builds never install.** A build is portable when a `go.mod` sits next to the exe or one folder up, a `portable` file sits next to it, or `RESOUND_PORTABLE=1` is set.

## Data files (`%LOCALAPPDATA%\Resound`)

| File | Content |
|---|---|
| `config.json` | Devices (endpoint ID and name: a chosen device whose ID changed, as Voicemeeter's do at every Windows start, is found again by its name), volumes, mic, keybinds (global and per app) and options, folders, server port, where the user moved the panel |
| `library.json` | Sound index: records with stable IDs, fingerprints, lengths, settings, phone layouts, tombstones |
| `sounds.json.migrated` | Per-sound settings of earlier versions, kept after migration |
| `remote.json` | Paired devices, the device secret their keys derive from, the connection's certificate |
| `installed_version.txt` | Version of the installed copy; an older exe started later asks before replacing it (starting the installed copy is the default) |
| `update\` | A downloaded update, only until the updated copy has started |
| `vbcable-install.json` | A VB-Cable install waiting for the Windows restart (removed after it) |
| `vbcable\` | The downloaded VB-Cable pack, only while its setup runs |
| `backups\` | Backup zips (`Resound-backup-<date>_<time>.zip`) and `index.json`, which also lists backups saved elsewhere |
| `debug.log` | Log and crash output; over 2 MB at start it moves to `debug.old.log`. Every line leaves out the user's name in paths (`C:\Users\<user>\…`), the computer's name, OneDrive organisations and email addresses (`logx.Scrub`); Diagnostics → Copy log scrubs the whole file again, crash output and older lines included. Sound, folder and device names stay |
| `running.json` | Version, pid and start time of the running instance; left behind means the run ended without a clean exit, which the next start logs |

## Key technical choices

| Choice | Why |
|---|---|
| Go without cgo | Plain `go build`. The same workflow as the Seed Helper, one small exe |
| Own WASAPI render loop (go-wca) | `oto` can't pick a device or open two streams; `malgo` needs cgo. Long-lived streams also beat Soundux's device-per-play |
| Decode with beep while playing, from the original file | Pure Go decoders; no duplicate of the library on disk, no warm-up, edits are always heard. Decoding is far faster than real time, so starts take milliseconds |
| One decoder per sample rate, fanned out to the outputs | Two outputs don't double the CPU work |
| Small ring per output | Memory doesn't grow with sound length or library size; Windows' file cache keeps recently played files fast for free |
| Fingerprint of head and tail, header probes | Indexing reads at most a few hundred KB per file, even for large libraries |
| Stable IDs for identity | Renames and moves keep settings |
| No decoded-audio cache | Tried in 0.6 development: ~11 MB per minute of audio and seconds of decoding per music file, for a start-up gain of a few milliseconds |
| Win32 + GDI panel instead of WebView | No WebView2 runtime or NuGet; tiny; full control over tray behaviour |
| Rows rebuilt per render | No widget state to keep in sync; pages and wizards are plain functions |
| Elevated one-shot helpers | The app never runs as admin; only the two admin writes do |
| IDs assigned once (initially the path hash) | Stable across restarts, removed tabs, renames and moves, unlike Soundux's list indexes |
| JSON index instead of a database | Thousands of sounds are a few hundred KB; loads in milliseconds, readable when debugging, no dependency |
| Phone app on an HTTPS host, WebRTC to the PC | A secure context (install, wake lock, offline start) without certificates on the PC or a server in between; the remote speaks the Soundux Remote API, so its front end carried over |

**go-wca workarounds** (all in `wincom` or `routing`; avoid the go-wca versions of these calls):
- `IMMDevice.Activate` passes a pointer where the class-context flag belongs. Use `wincom.Activate`.
- `IMMDeviceEnumerator.GetDevice` is an empty stub. Use `wincom.Find`.
- `IAudioEndpointVolume.GetMute` writes a 4-byte BOOL into a 1-byte Go bool, which corrupts memory. Use `wincom.GetMute`.
- `IPropertyStore.SetValue` and `Commit` are empty stubs. `routing` calls them directly.

## Known issues and gaps

Ordered by impact on reliability. None blocks normal use. Fixed in 0.6: concurrent writes to `sounds.json`, edited files playing old audio, long sounds held fully in memory, decoded clips accumulating in memory.

1. **The mic or push-to-talk can stay held.**
   - (a) If the process is killed during playback, the mic stays muted and a held key stays down until it is physically pressed. Sign-out, restart and shutdown are handled (`WM_ENDSESSION`); a crash or a Task Manager kill is not. Fix: persist "muted by Resound" and undo it on start.
   - (b) Engine events are dropped when their channel is full. A lost `EventFinished` keeps `remaining` non-empty, so the mic and PTT stay held. Fix: while holding, regularly compare `remaining` with `engine.Voices()`.
2. **Device changes are not followed.** There is no `IMMNotificationClient`: "System default" doesn't follow Windows' default device, and an unplugged device stays failed until "Restart outputs". Fix: register for endpoint notifications and reopen affected outputs.
3. **Updates if the old instance won't quit.** If the running copy doesn't exit within 5 s, the new copy starts, finds the single-instance mutex, and exits, so the old version keeps running. Fix: wait for the old process (not just its window), or show an error.
4. **Uninstall leftovers.** The firewall rule (deleting it needs admin) and the "Listen to this device" setting remain. Fix: offer an elevated cleanup, and record what Resound changed.
5. **Version info.** `winres.json` and `app.Version` hold development defaults. Release builds must override both; `scripts/build-release.ps1` does (and the release workflow uses it).
6. **A broken `config.json` resets silently** to defaults and is overwritten on the next save. Fix: back up the broken file and log it.
7. **Output failure releases holds for both outputs.** `EventOutputFailed` clears all held voices, releasing the mic and PTT even if the other output is still playing.
8. **The app comes from its host.** Installing it, and updates, need the host (Cloudflare Pages); an installed app starts from its cache. Phones must be on the PC's network: there is no relay for other networks.
9. **Elevation with a different admin account.** When a standard user approves UAC with another account, the helper's log goes to that account's `%LOCALAPPDATA%`.
10. **Front end** (planned): talk-through button bounces, 250 ms polling instead of live updates.
11. **No live file watching.** Changes on disk are picked up by the 5 s rescan on phone requests, the panel's "Refresh", and the check on every play. Fix if needed: `ReadDirectoryChangesW`.
12. **ReFS and network drives** may not provide stable file IDs; renames there are matched by fingerprint instead, which needs the file to have been indexed before it moved.
13. **VB-Cable's silent install is not officially documented.** `-i -h` is the switch named on VB-Audio's forum; should a future setup ignore it, its dialogs show (it is started visibly for that reason). The pack's readme asks for the author's agreement before integrating it into another installer, while the newer licensing page allows it under the donationware conditions. Get a written confirmation from VB-Audio before a public release.
14. **The meters record.** To show the levels of the microphone and of "CABLE Output", Resound records from them while the audio flow is on screen, so Windows 11 shows its microphone-in-use icon then and lists Resound under the microphone privacy settings. Nothing is kept. Windows offers no meter for a capture device that nobody records from.
15. **Untested packages.** `install` and the `_windows.go` audio paths have no automated tests; `app` only for the library and setup helpers; `ui` for its logic, offscreen rendering (flow, library rows, icons) and reading dropped links through OLE, but not for a real drag from another program. They are checked by vet and manual testing.
16. **Focus after a drop.** Windows may not let the panel take the foreground from the browser a link was dragged from; the name field then gets the keyboard on the first click into the panel.
17. **The editor is a third party.** Cutting sounds depends on audiocutter.online being up and keeping its postMessage API (`session` with a `File`, `output.mode: 'postmessage'`). Its docs aren't consistent and it publishes no versioning or terms for integrations. An app whose service worker predates `/edit` serves the landing page there until it has updated (as for `/help/`).
